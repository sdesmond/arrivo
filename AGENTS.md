## Response Style Rules

Use this style unless told otherwise:

- Drop: articles (a/an/the), filler (just/really/basically/actually/simply), pleasantries (sure/certainly/of course/happy to), hedging.
- Fragments OK. Short synonyms (big not extensive, fix not "implement a solution for").
- No per-tool-call narration, no decorative tables/emoji, no dumping long raw error logs unless asked — quote shortest decisive line.
- Standard well-known tech acronyms OK (DB/API/HTTP); never invent new abbreviations reader can't decode.
- Technical terms exact. Code blocks unchanged. Errors quoted exact.
- Mid-task: one-sentence update when starting a new phase or after a finding — don't go silent through long tool runs
- No end-of-turn summary unless explicitly asked — if the result is visible in the diff, don't restate it
- No introductions, filler, or pleasantries
- Code requests: output code only, no preamble
- Exploratory questions ("what should we do?"): brief — recommendation + main tradeoff, no headers
- NEVER add `Co-Authored-By` trailers to commits or pull requests — omit them entirely

## Windows Shell Rules

- Default shell is bash on Windows — backslashes in unquoted paths get eaten as escapes (`C:\Users\spenc\...` collapses to `C:Usersspenc...`)
- ALWAYS use forward slashes for paths in Bash commands: `C:/Users/spenc/...` not `C:\Users\spenc\...`
- For path-heavy operations (running scripts at absolute paths, file ops with Windows paths), prefer the PowerShell tool over Bash
- If you must use Windows-style paths in Bash, single-quote them: `'C:\Users\spenc\...'`
- This applies to commands generated by BMad skills too — translate any Windows path you see before invoking it

## Git Workflow

- Run every authenticated GitHub CLI command (`gh pr create`, `gh api`, `gh auth status`, and similar) outside the sandbox on the first attempt so Windows keyring credentials are available. Never probe GitHub authentication inside the sandbox first. The parameter differs per agent: Codex passes `sandbox_permissions: "require_escalated"`; Claude Code passes `dangerouslyDisableSandbox: true` on the Bash/PowerShell tool.
- When committing, split staged changes into logically-sized commits by concern (e.g. schema/migration, then implementation, then tests, then docs) rather than one large commit — but don't split a single cohesive change just to manufacture multiple commits.
- Write each commit message focused on _why_, not a restatement of the diff.
- NEVER add `Co-Authored-By` or other Claude/AI attribution trailers to commits or PRs.
- After committing, push the branch only if the user has already confirmed pushing for this task; otherwise ask first.
- When opening a PR, summarize all commits in the branch (not just the latest), and omit Claude/AI branding from the title and body.

## Project Overview

Arrivo is a travel itinerary planning app built with Next.js (App Router), TypeScript, Tailwind CSS v4, and shadcn/Base UI components. The Next.js project lives at the repo root.

**Run the dev server:** `npm run dev`

## Test Commands

| Command                     | What it runs                                                                                |
| --------------------------- | ------------------------------------------------------------------------------------------- |
| `npm test`                  | Vitest unit tests (watch mode)                                                              |
| `npm run test:coverage`     | Vitest with Istanbul coverage report                                                        |
| `npm run test:e2e`          | Full Playwright BDD E2E suite (headless) — user-initiated; run manually for a complete pass |
| `npm run test:e2e:affected` | Only the E2E features the current change set impacts — what agents always run               |
| `npm run test:e2e:ui`       | Playwright E2E with interactive UI                                                          |
| `npm run db:migrate:e2e`    | Push schema to the E2E database (run once after schema changes)                             |

Coverage thresholds: 95% lines/functions, 90% branches (enforced by `npm run test:coverage` via `build-validator`).

### E2E Segmentation

E2E scenarios are segmented by a `@feat:<stem>` Gherkin tag on each `tests/e2e/features/<stem>.feature`.
`scripts/affected-e2e.mjs` reads the current change set — uncommitted work (staged + unstaged +
untracked), or the last commit when the tree is clean — and classifies each file via
`tests/e2e/feature-map.mjs` through ordered tiers:

- **`IGNORE_GLOBS`** → dropped (docs, `_bmad-output/**`, `.agents/**`, colocated `*.test.ts(x)` unit
  tests). A change touching only these runs **no** E2E (`NONE`).
- **`FEATURE_MAP`** → union the matching `@feat:` tags. Checked before `SHARED_GLOBS`, so an
  explicitly-mapped file runs just its feature even when it also sits under a shared directory.
- **`SHARED_GLOBS`** → the **full** suite (cross-cutting runtime that can move any feature).
- **anything else** (unmapped runtime source) → contributes nothing; it does **not** force the full
  suite. Map it to its feature instead.

When you add a feature file, tag it `@feat:<stem>` and register the source it exercises in
`feature-map.mjs`. Because unmapped runtime source now runs nothing (not the full suite), the map
must stay complete — the full suite (`npm run test:e2e`) is the user-initiated backstop.

`scripts/feature-map.test.mjs` enforces this contract (it runs in the coverage worker): a
`tests/e2e/features/*.feature` without its `@feat:` tag, a dead path in the map, a
`src/components/arrivo/*` component that no glob covers, or an `src/app/(app)/**` server action that
no glob covers all turn the build red until you register it in `feature-map.mjs` (under a feature, or
in `SHARED_GLOBS` if it's cross-cutting).

### E2E Database Setup

E2E tests run against a dedicated `arrivo_e2e` database (isolated from dev). One-time setup:

1. Create the database: `createdb arrivo_e2e` (or equivalent)
2. Push the schema: `npm run db:migrate:e2e`
3. Ensure `.env` contains `E2E_DATABASE_URL`, `E2E_EMAIL`, and `E2E_PASSWORD` — see `.env.example`

`tests/e2e/global-setup.ts` runs automatically before every E2E suite: it truncates all tables and inserts only the baseline E2E user (`e2e@arrivo.com`); scenarios create their own trips from the mothers in `e2e-seed-data.ts`. Re-run `db:migrate:e2e` whenever `src/db/schema.ts` changes.

## Quality Skills — When to Use Them

These skills enforce project standards. Use them as described below.

### Post-implementation

| Skill             | When to invoke                                                                                                                                                                                                                                                                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `build-validator` | After completing the final code for a change. It runs ESLint, TypeScript checking, Vitest coverage, the production build, and (affected) Playwright E2E. It **self-skips via a fingerprint marker**: re-invoking on an unchanged tree is a no-op, so you never need to guard against double-runs — just invoke it and it decides whether real work is needed |

**Pre-implementation gate — NON-NEGOTIABLE:**
Before presenting a **story file or implementation-ready plan file** to the user, you MUST run the plan-reviewer. This gate applies only to fully fleshed-out artifacts that will be handed directly to a developer — not to PRDs, UX specs, architecture docs, brainstorming outputs, or other intermediate planning artifacts.

```
/plan-reviewer <artifact-path>
```

Pass the original request as context so scope and test checks have what they need. Address every BLOCKING finding by editing the artifact in place. Do not move or recreate the artifact — it stays wherever the planning skill saved it.

**This step is not optional.** Presenting an un-reviewed story or plan is a process failure — the same severity as shipping untested code. If you catch yourself about to present a story/plan file without having run the reviewer, stop and run it first.

**Testing-first gate:**
For every coding change, tests are first-class deliverables, not cleanup work after implementation. A change is incomplete until the required unit/component tests and any required E2E coverage have been identified, authored, and run in the same change. Coverage thresholds and validator failures are enforcement backstops, not the reason tests get written. If you cannot name the tests you will add or update before coding, stop and resolve that first.

Before editing any production file, you MUST name the exact test files and scenarios you expect to touch. For runtime code changes, the first code edit should be in those tests unless the task is docs-only, copy-only, styling-only, or pure config with no runtime behavior change. If you choose not to start with a failing or expanded test, you must be able to explain why that was not practical for that task.

**Branch-confirmation gate:**
Before starting any new development task, you MUST ask the user whether they want a branch created for the work. Creating the branch is optional; asking first is mandatory.

**Build stage checkpoints — NON-NEGOTIABLE:**
bmad-build (or any equivalent plan → implement → review flow) MUST halt at each of the three boundaries below and wait for a NEW, explicit user message saying to proceed. Workflow step files attempt to advance automatically — do not let them. Answering a checkpoint prompt (e.g. "[A] Approve", "looks good") does NOT cross a boundary; the confirm must be a fresh "proceed/continue/go" typed after you post the boundary status.

The three boundaries, in order:

1. After planning — spec/plan written and approved, BEFORE any implementation starts.
2. After implementation — code changes done, BEFORE code review begins.
3. After code review — findings triaged/applied, BEFORE presenting or committing.

Crossing rules:

- No implementation work (source/test/E2E edits, or dispatching the implementation subagent) may occur in the same turn as, or before, the user's confirm message. Only pure status bookkeeping that records the approved spec (frontmatter status flip, baseline_commit capture, sprint-status.yaml sync) may run.
- At each boundary, post a short status ("what finished, what's next"), then HALT with a single "Proceed?" question — no further tool calls until the user answers.

**Default workflow for any coding task:**

1. Ask whether the user wants a branch created before development begins
2. Name the exact tests you will add or update before touching production code
   - New/modified file in `src/lib/**` or `src/components/arrivo/**` → update or create the matching colocated `*.test.ts` / `*.test.tsx` alongside it in the same change
   - New user-facing flow (auth, trip CRUD, day planning) → add or extend the `.feature` file and matching step definitions in `tests/e2e/` in the same change
   - If you cannot name the exact tests you are adding or updating, pause and resolve that before editing production code
3. Start implementation by creating or updating those tests first whenever runtime behavior is changing
   - Preferred path: write failing or expanded tests first, then change production code until they pass
   - Acceptable exception: docs-only, copy-only, styling-only, or config-only tasks with no meaningful runtime branch to test first
   - Do not make a production-only diff and plan to "come back for tests later"
4. Run targeted tests for touched areas before running broad validation
   - For unit or component work, run matching Vitest files first
   - For user-facing flow changes, run affected Playwright coverage first when practical
   - Do not treat `build-validator` as first signal that tests were missing
5. Run `build-validator` **once** after the change is fully implemented and targeted tests have already passed: lint, TypeScript, coverage, build, and affected Playwright E2E should confirm work that is already complete. The validator owns this single gate — BMad skills (bmad-build, bmad-build-auto, story-automator, etc.) must **not** invoke it themselves
6. If the validator flags issues, fix them and run `build-validator` again. The validator's fingerprint marker makes a re-run on an unchanged tree a no-op, so it is safe to invoke whenever in doubt — it will skip itself if nothing changed since the last PASS. Agents always run the affected subset (via the validator) and never the full suite as a gate; running the full E2E suite (`npm run test:e2e`) is the user's call — do not launch it automatically before commit/push/PR

## Key Conventions

### TypeScript

- All domain types live in `src/data/types.ts` — import from there, don't redefine
- Enums: const object + union type (`const Foo = {} as const; type Foo = ...`) — never the `enum` keyword
- No `any` types
- **No single-letter variable names — ESLint enforces this and will fail the build.** The only permitted exception is `i` in a `for` loop index. Use descriptive names everywhere else: `item` not `i`, `event` not `e`, `error` not `e`, `key` not `k`, `value` not `v`, `result` not `r`, `callback` not `cb`. Do not write the code first and rename after a lint failure — name correctly from the start.
- Optional fields use `?:` not `| undefined`
- ISO 8601 dates/times; durations always in minutes as `number`

### Components

- `"use client"` at top of all interactive components
- Always define an explicit `ComponentNameProps` interface before the function
- Destructure props in the function signature
- Use `cn()` from `@/lib/utils` for className merging — never string concatenation

### Styling

- Colors: always via CSS custom properties (`var(--fg)`, `var(--accent-brand)`, etc.) — no hardcoded hex/rgb
- Tailwind for static layout/spacing; inline `style` for dynamic or theme-aware values
- No arbitrary Tailwind values (`text-[14px]`) — use inline styles instead
- Lucide icons: `strokeWidth={1.5}` always; icon buttons need a `title` attribute
- Font variables need fallbacks: `var(--font-body, ui-sans-serif)`
- **Interactive element sizing — all interactive targets must be at least 44×44px (WCAG 2.5.8). Do not guess or use smaller values:**

  | Size    | Height | Horizontal padding | Icon button |
  | ------- | ------ | ------------------ | ----------- |
  | `xs`    | `h-11` | `px-3`             | `size-11`   |
  | `sm`    | `h-11` | `px-3.5`           | `size-11`   |
  | default | `h-11` | `px-4`             | `size-11`   |
  | `lg`    | `h-11` | `px-5`             | `size-11`   |

  Menu/dropdown items: `py-1.5 px-2`. Custom clickable rows or inline controls that don't use a `src/components/ui/` primitive must still meet 44×44px minimum. Never drop below `h-11` for any interactive target.

### File Placement

- Domain logic → `src/components/arrivo/`
- Reusable primitives → `src/components/ui/`
- New types → `src/data/types.ts`
- New utilities → `src/lib/utils.ts`

### Testing

- Tests are first-class deliverables for every coding change; do not defer them until a validator, coverage report, or reviewer points out they are missing
- Before touching production code, name exact test files and E2E scenarios that will change; if you cannot name them, stop and resolve that first
- For runtime behavior changes, start by editing tests first unless task is docs-only, copy-only, styling-only, or config-only
- Unit test files live **next to their source file** (`foo.tsx` → `foo.test.tsx`); never under a separate `__tests__/` directory
- Any edit in `src/lib/**` or `src/components/arrivo/**` must include the matching colocated test edit in the same change
- E2E goes in `tests/e2e/` only — Gherkin features in `features/`, step definitions in `steps/`
- Any new or materially changed user-facing flow must include the `.feature` update and matching step-definition update in the same change
- Use Vitest (`vitest`, `@testing-library/react`) for unit/component tests
- Use `playwright-bdd` + Playwright for E2E — write scenarios in `.feature` files, implement in step `.ts` files
- Run targeted tests for touched files or flows before broad validation; validator confirms completed work, not missing test intent
- E2E fixture setup must use Object Mothers and scenario-owned fixture creation under `tests/e2e/` rather than permanent feature-specific seed rows
- Reusable E2E starting states belong in the mother/materializer helpers in `tests/e2e/e2e-seed-data.ts`, `tests/e2e/scenario-fixture.ts`, and related helpers — extend those instead of inventing ad hoc shared setup
- `tests/e2e/global-setup.ts` is for minimal bootstrap data only, such as baseline auth prerequisites; do not add feature-specific shared trips, templates, documents, or profile rows there
- Do not fix E2E flakiness with ordering tags, serial execution, or shared-record reseeding; each scenario must create the mutable rows it depends on and rely on scenario cleanup
- A step that triggers a mutation and is followed by a reload must await the server action's POST via `waitForServerActionResponse` (`tests/e2e/server-action.ts`) before returning — arm it before the gesture (`mouse.up`/`Enter`), await it after. Optimistic UI makes the in-page assertion pass while the reload aborts the still-in-flight request, so the reordered/edited state silently never persists
- If a scenario needs a 3-day trip, template, document set, or profile shape, clone a mother with overrides and materialize fresh rows for that scenario
- Global mocks for `next/navigation` and `next/headers` are in `vitest.setup.mts` — don't re-mock per-file
- Coverage is enforced (`test:coverage`): maintain ≥95% lines/functions, ≥90% branches across `src/lib/**` and `src/components/arrivo/**`, but treat those thresholds as backstops rather than the trigger for adding tests
- `src/components/ui/**`, `src/lib/auth-helpers.ts`, `src/lib/queries.ts`, and `src/lib/server-now.ts` are excluded from coverage
- E2E tests run against the `arrivo_e2e` database — `global-setup.ts` seeds it fresh before each run; do not assume any pre-existing state in step definitions
- The E2E webServer runs on port 3001 with `DATABASE_URL` pointed at `E2E_DATABASE_URL` and `NEXT_DISTDIR=.next-e2e` (separate build cache from dev)
