## Response Style Rules

- NEVER start with 'Let me' or 'Let's' — use present-participle gerunds instead: 'Looking into...', 'Running tests...', 'Found X in Y', 'Checking...'. NEVER start a sentence with "Now..." for example, "Now looking into...," "Now changing..." It can be assumed that you're doing the thing now so there's no need to say it.
- One sentence per mid-task update; state the action or finding only
- No end-of-turn summary unless explicitly asked — if the result is visible in the diff, don't restate it
- No introductions, filler, or pleasantries
- Code requests: output code only, no preamble
- Exploratory questions ("what should we do?"): 2–3 sentences max, recommendation + tradeoff, no headers

## Windows Shell Rules

- Default shell is bash on Windows — backslashes in unquoted paths get eaten as escapes (`C:\Users\spenc\...` collapses to `C:Usersspenc...`)
- ALWAYS use forward slashes for paths in Bash commands: `C:/Users/spenc/...` not `C:\Users\spenc\...`
- For path-heavy operations (running scripts at absolute paths, file ops with Windows paths), prefer the PowerShell tool over Bash
- If you must use Windows-style paths in Bash, single-quote them: `'C:\Users\spenc\...'`
- This applies to commands generated by BMad skills too — translate any Windows path you see before invoking it

## Project Overview

Packt is a travel itinerary planning app built with Next.js (App Router), TypeScript, Tailwind CSS v4, and shadcn/Base UI components. The Next.js project lives at the repo root.

**Run the dev server:** `npm run dev`

## Test Commands

| Command                  | What it runs                                                    |
| ------------------------ | --------------------------------------------------------------- |
| `npm test`               | Vitest unit tests (watch mode)                                  |
| `npm run test:coverage`  | Vitest with Istanbul coverage report                            |
| `npm run test:e2e`       | Playwright BDD E2E tests (headless)                             |
| `npm run test:e2e:ui`    | Playwright E2E with interactive UI                              |
| `npm run db:migrate:e2e` | Push schema to the E2E database (run once after schema changes) |

Coverage thresholds: 95% lines/functions, 90% branches (enforced in CI).

### E2E Database Setup

E2E tests run against a dedicated `packt_e2e` database (isolated from dev). One-time setup:

1. Create the database: `createdb packt_e2e` (or equivalent)
2. Push the schema: `npm run db:migrate:e2e`
3. Ensure `.env` contains `E2E_DATABASE_URL`, `E2E_EMAIL`, and `E2E_PASSWORD` — see `.env.example`

`tests/e2e/global-setup.ts` runs automatically before every E2E suite: it truncates all tables and re-seeds with fixed data from `e2e-seed-data.ts` (user `e2e@packt.local`, one trip, three days). Re-run `db:migrate:e2e` whenever `src/db/schema.ts` changes.

## Quality Agents — When to Use Them

These agents enforce project standards. Use them as described below — don't skip them.

### Post-implementation agents

| Agent                   | When to invoke                                                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packt-build-validator` | After any code change and again before committing; runs ESLint, TypeScript checking, Vitest coverage, the production build, and Playwright E2E validation |
| `desktop-reviewer`      | After visual changes when browser validation is needed; run sequentially with `mobile-reviewer` (NOT in parallel — they share one Playwright browser)     |
| `mobile-reviewer`       | After visual changes when browser validation is needed; run sequentially with `desktop-reviewer` (NOT in parallel — they share one Playwright browser)    |

**Pre-implementation gate — NON-NEGOTIABLE:**
Before presenting any planning artifact (PRD, UX spec, architecture doc, story, plan file) to the user, you MUST run the packt-plan-reviewer.

```
/packt-plan-reviewer <artifact-path>
```

Pass the original request as context so scope and test checks have what they need. Address every BLOCKING finding by editing the artifact in place. Do not move or recreate the artifact — it stays wherever the planning skill saved it.

**This step is not optional.** Presenting an un-reviewed plan is a process failure — the same severity as shipping untested code. If you catch yourself about to present a planning artifact without having run the reviewer, stop and run it first.

**Default workflow for any coding task:**

1. Implement the change **and write/update the colocated test file** — tests are part of the same step, not an afterthought
   - New/modified file in `src/lib/**` or `src/components/packt/**` → update or create `*.test.ts` / `*.test.tsx` alongside it
   - New user-facing flow (auth, trip CRUD, day planning) → add or extend a `.feature` + step file in `tests/e2e/`
2. Run `packt-build-validator` to catch lint, TypeScript, coverage, build, and E2E failures
3. Fix any flagged issues, then re-run `packt-build-validator` again before the final commit

## Key Conventions

### TypeScript

- All domain types live in `src/data/types.ts` — import from there, don't redefine
- Enums: const object + union type (`const Foo = {} as const; type Foo = ...`) — never the `enum` keyword
- No `any` types; no single-letter variable names (except `for` loop `i`)
- Optional fields use `?:` not `| undefined`
- ISO 8601 dates/times; durations always in minutes as `number`

### Components

- `"use client"` at top of all interactive components
- Always define an explicit `ComponentNameProps` interface before the function
- Destructure props in the function signature
- Use `cn()` from `@/lib/utils` for className merging — never string concatenation

### Styling

- Colors: always via CSS custom properties (`var(--fg)`, `var(--accent-brand)`, etc.) — no hardcoded hex/rgb
- Tailwind for static layout/spacing; inline `style` for dynamic or theme-aware values
- No arbitrary Tailwind values (`text-[14px]`) — use inline styles instead
- Lucide icons: `strokeWidth={1.5}` always; icon buttons need a `title` attribute
- Font variables need fallbacks: `var(--font-body, ui-sans-serif)`

### File Placement

- Domain logic → `src/components/packt/`
- Reusable primitives → `src/components/ui/`
- New types → `src/data/types.ts`
- New utilities → `src/lib/utils.ts`

### Testing

- Unit test files live **next to their source file** (`foo.tsx` → `foo.test.tsx`); never under a separate `__tests__/` directory
- E2E goes in `tests/e2e/` only — Gherkin features in `features/`, step definitions in `steps/`
- Use Vitest (`vitest`, `@testing-library/react`) for unit/component tests
- Use `playwright-bdd` + Playwright for E2E — write scenarios in `.feature` files, implement in step `.ts` files
- Global mocks for `next/navigation` and `next/headers` are in `vitest.setup.mts` — don't re-mock per-file
- Coverage is enforced (`test:coverage`): maintain ≥95% lines/functions, ≥90% branches across `src/lib/**` and `src/components/packt/**`
- `src/components/ui/**`, `src/lib/auth-helpers.ts`, `src/lib/queries.ts`, and `src/lib/server-now.ts` are excluded from coverage
- E2E tests run against the `packt_e2e` database — `global-setup.ts` seeds it fresh before each run; do not assume any pre-existing state in step definitions
- The E2E webServer runs on port 3001 with `DATABASE_URL` pointed at `E2E_DATABASE_URL` and `NEXT_DISTDIR=.next-e2e` (separate build cache from dev)
