## Journey 1 — "seamless edit" happy path (2026-06-20)
- Protagonist: Theo (placeholder name pending user confirmation).
- Beats: arrives at destination → goes out to activities → loses reception mid-activity, doesn't notice → views events/times offline, makes a quick timing adjustment to an event → returns to hotel, reconnects to WiFi → trip silently syncs to server, no visible indication the edit ever happened offline.
- Climax beat: the non-event — reconnect causes zero visible UI change. This is the bar for the no-conflict sync path: silent, no toast, no modal, nav indicator just clears.

## Journey 2 — "conflict on reconnect" (2026-06-20)
- Protagonist: Theo, same trip. Edits an event for tomorrow while out; another device/collaborator also changed the trip while he was offline.
- Beats: reconnects at hotel → gets a notification that the trip changed while offline and needs attention → opens it, sees what changed and how it fits into his view of the trip → chooses to keep changes or discard them (his own changes included in that choice) → confirms → trip updates.
- Climax beat: the notification + review screen — first moment offline storage becomes visible to Theo at all.
- Resolution is per-item (keep/discard decided per changed item, not as one batch action).
- Notification on reconnect-with-conflict is attention-demanding (interrupting), not a passive toast/badge — contrast with Journey 1's fully silent no-conflict path.
- Attribution copy always names a collaborator slot; in v1 (no multi-collaborator UI yet) that slot always reads "You" since the only conflict source is the same user on another device.

## Surface — pending-sync badge folds into the connectivity indicator (2026-06-20)
- No separate "pending sync" badge surface. Ordinary offline edits syncing back on reconnect stay fully invisible — same slot as the connectivity indicator (home-view Bell slot, trip-view crumb slot, mobile dot) goes straight from `WifiOff` to hidden with no passive "syncing" interim state. This preserves Journey 1's non-event climax exactly: reconnect causes zero visible change when there's no conflict.
- The same slot only reappears, in a third state, when a conflict is found on sync: icon swaps to `CloudAlert` (warning/destructive color, matches existing Badge `warning`/`destructive` vocabulary) and becomes a clickable button that opens the conflict review screen.
- Conflict detection also fires an automatic interrupting toast/modal at the moment it's found — not just the icon change — matching Journey 2's "gets a notification that demands his attention" beat literally. Exact mechanism (blocking modal vs. interrupting toast that deep-links into the review screen) is decided alongside the conflict review screen surface itself, since it's the same moment.
- Net icon states for the one shared slot: hidden (default) → `WifiOff` (offline) → `CloudAlert` (conflict needs attention, clickable, paired with an interrupting toast/modal at detection time).

## Surface — conflict review screen (2026-06-20)
- Detection-time interrupting modal offers exactly two choices: "Resolve now" (opens the review screen immediately) or put it off. Putting it off leaves the `CloudAlert` icon as the re-entry route back to the same review screen later.
- The review screen itself is a full takeover dialog — not dismissable by clicking away or (implicitly) Escape; must be resolved to close. No snooze-from-inside affordance has been stated yet (open — see follow-up question).
- Content:
  - Incoming-only changes (no local edits on this trip while offline): list every added/removed item, each with independent Accept/Decline.
  - Local + incoming changes both present: all changes from both sources are listed together — every item clearly tagged **Local** vs **Online** — each with independent Accept/Decline.
  - Same item edited differently on both sides (true conflict, not a pure add/remove): rendered as two competing entries — one tagged Local with its value, one tagged Online with its value — mutually exclusive (accepting one auto-declines its pair), distinct from the independent-accept/decline rows used for plain adds/removes.
- Resolution stays per-item (confirmed earlier in Journey 2), not a single batch accept-all/discard-all action.
- Truly one-way once opened: no "finish later" from inside the review screen — once it's open, every item must be resolved before it closes. The only exit point before resolution is declining "Resolve now" at the initial interrupting modal, which leaves the `CloudAlert` icon as the sole re-entry route.

## Surface — document conflicts narrowed, no separate screen (2026-06-20)
- **Deviation from the PRD addendum**, to reconcile with the PRD later: the addendum's "documents = review-merge" is narrowed. Documents do NOT get a full diff/merge UI — too costly to show "which doc to keep" meaningfully, and the app already allows duplicate document names, which removes most of what would otherwise look like a naming conflict.
- Default for documents is silent auto-merge (same as packing list) — renames, retags, two independently-uploaded docs that happen to share a name: no prompt, nothing lost, no review needed.
- One exception, to hold the line on NFR1 (no sync path may silently discard data): a **document deletion conflict** — local deleted a doc while offline and it still exists/changed online, or vice versa — does need review, because deletion is destructive and silent existence-wins-by-default could surprise the user either way.
- That exception does NOT get its own screen. It folds into the same itinerary conflict review screen as just another row: "Document removed while offline," tagged Local/Online like other rows, Accept (confirm removal) / Decline (keep the document). One unified review screen for every conflict type that actually needs a decision; nothing document-specific to build separately.
- Packing list stays exactly as the addendum already states: last-write-wins, no prompt, never enters this screen.

## Surface — OQ1 resolved: storage-can't-fit failure UX (2026-06-21)
- FR13 (prd.md:62) already settles the all-or-nothing question: "no partial or corrupted local state results" — a failed pin/sync rolls back rather than keeping a partial download. OQ1's remaining open part was just the failure's visible UX, not whether partial state is allowed.
- TripCover icon gets a fourth state: `CloudAlert` (reuses the same icon already chosen for the connectivity indicator's conflict state — one icon, one meaning, "needs attention," across surfaces rather than inventing a new error glyph). Persists until the user acts, rather than silently reverting to `Download` — keeps a failed pin visible even if the user missed the toast that fired at failure time.
- At failure: interrupting toast names the reason ("Not enough storage to pin this trip") with Retry / dismiss. Clicking the persistent `CloudAlert` icon afterward reopens the same explanation/Retry, mirroring how the connectivity indicator's `CloudAlert` re-enters the conflict review screen.
- Mid-sync storage failure (can't fit incoming changes during reconnect sync) gets the same toast treatment as a pin failure — not the heavier interrupting modal reserved for conflicts, since FR13's rollback guarantee means no data is at risk, just a wait/retry.

## Surface — OQ2 resolved: no pre-pin size warning (2026-06-21)
- Decided not to add a pre-pin size estimate/confirm step. The OQ1 failure path (`CloudAlert` + toast + Retry) already covers the case where a trip genuinely doesn't fit — a second, separate "this might be large" warning would duplicate that backstop for a case that's rare in practice (trip docs/images, not video).
- Net effect: TripCover's direct-toggle pin gesture (Download → progress ring → CloudCheck, or CloudAlert on failure) stays exactly as already decided — no added confirm step for any trip size. OQ2 closes with no new surface.
