# Epic 4 Retrospective: Live Sync and Revocation

## Epic summary

Epic 4 layered Server-Sent Events (SSE) live sync and immediate access revocation on top of the
existing trip-sharing feature: contributors see itinerary/membership changes across open sessions
without a manual refresh, know when their live connection has dropped, and a removed contributor is
told immediately and cannot get back in, even mid-session (`_bmad-output/implementation-artifacts/epic-4-context.md`).

**Stories (all `done` per `sprint-status.yaml`):**

- 4.1 SSE pub-sub infrastructure and both routes
- 4.2 Sync status indicator
- 4.3 Trip page live refresh on itinerary and membership events
- 4.4 Revocation modal on self-targeted removal
- 4.5 Dashboard reflects membership changes live
- 4.6 Move sync status indicator to a top-bar icon (added post-hoc, not in the original epics doc — see spec-4-6 Spec Change Log)

Plus one post-epic bugfix bundled into this retro's scope because it patches a gap the epic itself
shipped with: **`spec-heartbeat-fanout-health-check.md`** ("Route SSE heartbeat through the pub/sub
fan-out path", merged as PR #271, 2026-09-08) — the SSE heartbeat proved only that the HTTP
connection was open, never that `publishTripEvent`/`publishUserEvent` fan-out actually reached that
subscriber, so a broken fan-out would have reported healthy indefinitely.

landed** — the extraction shipped in commit `9b6d5be`/PR #271, so nothing further to route here. But
it is the clearest evidence in this epic that per-story review has a structural blind spot: near-
identical files that never land in the same diff never get compared. See process lesson below.

**God-class / size growth — none.** Ranked the top-churn files from `git_evidence.py`'s `files` list

### Diff-scope review (bmad-review: adversarial, edge-case-hunter, verification-gap)

#### verification-gap (complete)

**VG-1 — 24 of 30 `publishItineraryChanged(tripId)` call sites in `src/app/(app)/trips/[tripId]/actions.ts` have no regression test.**
Only 6 mutating actions (`createEvent`, `updateEvent`, `deleteEvent`, `deleteEventWithDocDecision`,
`addDay`, `removeLastDay`) have an `expect(mockPublishTripEvent).toHaveBeenCalledWith(...)` assertion
in `actions.test.ts` (lines 361-364, 403-406, 438-441, 475-478, 1223-1226, 1341-1344). The other 24 —
`reorderDayItems`, `updateDay`, checklist CRUD, note CRUD, document actions, cover actions — call the
same shared publish helper with no assertion backing it. `src/app/**` is excluded from coverage
thresholds, so nothing gates this, and the one multi-tab E2E scenario for this path
(`trip-live-refresh.feature`) only exercises an event-rename, which maps to the one already-asserted
`updateEvent`. **Consequence:** a future refactor that drops the publish call from, say, checklist
toggling ships silently — other open tabs simply stop live-refreshing for that mutation type, with no
test or coverage gate to catch it. Source: full read of `actions.ts` (30 call sites mapped) and
`actions.test.ts` (grep for `ItineraryChanged`/`mockPublishTripEvent`, exactly 6 matches).

**VG-2 — `use-live-sync.ts`'s client-side fan-out has no per-listener throw isolation, unlike its server-side counterpart.**
`trip-events.ts`'s `deliverToTripSubscribers`/`deliverToUserSubscribers` wrap each subscriber
callback in try/catch specifically so "one throwing callback never blocks the rest" — covered by 4
dedicated tests. The client-side mirror in `use-live-sync.ts` (`broadcastStatus`'s
`statusListeners.forEach` and `onmessage`'s `eventListeners.forEach`) has no equivalent guard, and no
test drives a throwing listener. This matters because `SyncStatusIndicator` and
`ContributorRevocationModal` are both mounted on the same shared personal channel in
`(app)/layout.tsx`, plus `useDashboardLiveRefresh` when the dashboard is open — one listener throwing
would silently suppress delivery to whichever listeners iterate after it in the same tick, no logging,
no test. **This is not a fresh finding** — `spec-heartbeat-fanout-health-check.md`'s own review
findings already recorded it verbatim as "deferred, pre-existing," and the fix's task list
deliberately scoped around it (fixed the `releaseChannel` identity guard and abort-enqueue guard, left
this one). Confirmed still present in current `use-live-sync.ts`.

#### adversarial (complete — 14 findings, third launch attempt; first two failed on a transient API 400 error before producing output)

**AD-1 / AD-2 — `removeTripSubscribersForUser`/`purgeTripTopic` (the force-removal/delete paths) leak the underlying SSE connection and skip the cleanup the normal unsubscribe path performs.**
Confirmed by direct read (`trip-events.ts:210-232`, reproduced above under EC-1/EC-2): both functions
delete the `TripSubscriber` entry from the in-memory Set but never invoke the per-connection
`unsubscribe()`/`controller.close()` that `createLiveSyncResponse` ties to the request's
`AbortSignal`. Consequence, per the adversarial framing (goes further than EC-1/EC-2's "scheduler
keeps ticking" framing): the revoked/removed viewer's HTTP response and `ReadableStream` stay open on
the server indefinitely — no more heartbeats reach it (it's no longer in the topic), so it goes dark
rather than erroring, and the client's `EventSource` never fires a native reconnect because nothing
ever errored from its side either. **Three independent passes (EC-1, EC-2, and this adversarial pass)
converged on the same root cause from different angles** — the strongest-corroborated finding in this
retro.

**AD-3 — an open trip page never reacts to `trip-deleted`.**
`use-trip-live-refresh.ts:6-9,15` explicitly excludes `TripDeleted` from `REFRESH_EVENT_TYPES`, with a
comment stating "`membership-removed`/`trip-deleted` frames are left alone — those are 4.4/4.5
concerns." Verified: neither story 4.4 (revocation modal, self-targeted removal only) nor 4.5
(dashboard membership changes) actually covers a *different* collaborator's open trip page reacting
to that trip being deleted out from under them. Story 4.1's own AC required only that the event
"publishes to `trip:{tripId}` so any open connection is told rather than orphaned" — technically true
at the transport level, but no client ever consumes the frame. A viewer with the trip open sees no
redirect, no message, nothing — a zombie page until they attempt a mutation and hit a generic
`notFound()`, or navigate away manually.

**AD-4 — other collaborators' dashboards don't reflect a trip deletion live either, contradicting FR8 for this one case.**
`use-dashboard-live-refresh.ts`'s own doc comment states "`trip-deleted` is likewise ignored —
deletions stay `revalidatePath`-driven." Verified: `revalidatePath` only invalidates the Next.js cache
for the *acting* user's own request path; it does not push to other already-rendered sessions in
other tabs/devices. A different collaborator with their dashboard open keeps seeing the deleted trip
until they manually reload — the exact cross-session case FR8 ("shared trip state... updates live
across sessions without a reload") exists to solve. AD-3 and AD-4 are the same root gap (trip
deletion was never wired into either live-refresh hook) surfacing on two different surfaces.

**AD-5 — a role downgrade (not removal) while an editor-only dialog is open isn't force-closed the way full removal is.**
The force-close pattern story 4.4 built (`trips/[tripId]/page-client.tsx:145-162`) fires only on
self-targeted `MembershipRemoved`. A `MembershipChanged` event that lowers the viewer below what
their *currently open* dialog requires (e.g. editor demoted to viewer mid-edit) isn't handled the same
way — the eventual save is correctly rejected server-side via `assertTripAccess()`'s `notFound()`, but
the client shows a generic failure instead of proactively closing the now-invalid dialog.

**AD-6 — `publishItineraryChanged(tripId)` is called before `revalidatePath(...)` at all ~30 call sites in `actions.ts`, uniformly.**
Verified via grep: every site (228-229, 249-250, 273-274, 305-306, 359-360, 368-369, 414-415, and the
rest) publishes first, then revalidates. A subscriber's live-sync-triggered refresh could theoretically
race the cache invalidation it's meant to react to. The window is narrow (network latency to the
subscriber vs. an in-process `revalidatePath` call), and 11/11 E2E passed with no observed staleness,
but the ordering is systemically backwards from the safer invariant across the entire file rather than
being an isolated slip.

**AD-7 — `user.id` vs `user.id!` inconsistency between `acceptInvitation` and `declineInvitation`.**
Verified: `trips/actions.ts:840` uses `user.id` (bare) in `publishUserEvent`, `:877` uses `user.id!`
(asserted) for the identical call shape after the identical `if (!user.email || !user.id)` guard. No
runtime bug today — TypeScript narrows `user.id` after the guard either way — but a maintenance trap:
a future refactor of the guard could silently reintroduce a `string | undefined` at the one
unprotected call site while its sibling stays safe.

**AD-8 — global `viewportFit: "cover"` (story 4.6) affects every fixed/absolute element app-wide, not just the sync indicator.**
Real blast radius, but **not a new finding** — `spec-4-6`'s own Spec Change Log already identifies
this exact global effect explicitly ("This — not the spacer's position in the DOM — is why 4-2's
bottom-right pill overlapped the tab bar... The fix is global and also repairs
`bottom-tab-bar.tsx`"), reasoned through and accepted at review time. This retro's E2E run (11/11
passed, all four feature areas) surfaced no new visual regression from it. Recording as an already-
accepted, already-documented deviation — not routed as a new action item.

**AD-9 — single-instance-only in-memory pub/sub isn't documented inline in `trip-events.ts` itself, only implied by the singleton comment.**
The scope cut itself is legitimate and explicitly declared at the epic level
(`epic-4-context.md`: "No Redis / horizontal-scale fan-out this round — deferred... a multi-instance
deployment would silently break live sync and revocation and must swap in Redis first"). This finding
just asks for the same statement to live as an inline comment in the file that would break, not only
in the epic doc. Low-effort doc-only improvement.

**AD-10 — RETRACTED after user correction (2026-09-08).** Originally claimed `tripName`/
`removedByEmail` could fall back to empty string and render broken revocation-modal copy. Re-checked
against the actual schema and call site and the claim doesn't hold:
- `trips.name` is `text("name").notNull()` in `src/db/schema.ts:92` — DB-enforced, cannot be null/empty
  on an existing row.
- The `tripRow` read (`trips/actions.ts:1034-1035`) happens *inside* the same `db.transaction` that
  already called `lockTripForUpdate(transaction, tripId)` at the top (`:989`) — the trip row is locked
  for the duration of this transaction, so it cannot have vanished by the time this `SELECT` runs. The
  `?? ""` fallback is unreachable in the removeCollaborator/role-change flow this code path serves.
- `users.email` is nullable at the DB level (`schema.ts:27`, no `.notNull()`), but the app has exactly
  one account-creation path — `src/app/(auth)/actions.ts:35`, `if (!email || !password || ...)
  return {error}` — and `src/auth.ts` wires only a `Credentials` provider, no OAuth provider that could
  create a user without an email. Every real session's `user.email` is populated in practice.

Both guards were defensive coding against a state the schema/flow already prevents, not a real gap.
**Disposition changed from "fix now" to "accept as-is — finding did not survive verification."** The
sprint-status action item this generated (`epic-4-retro-item-21`) is being closed as not-applicable,
not fixed. Kept in this document rather than deleted, per the skill's rule that a finding whose source
doesn't hold up is dropped, not silently erased — the record of the retraction is itself worth keeping.

**AD-11 — an editor's own mutation triggers a redundant second refresh via their own SSE echo.**
`publishTripEvent` doesn't exclude the publisher's own connection from fan-out, so an editor mounted
on the same trip page they're editing gets their own `itinerary-changed` event back, triggering a
second `router.refresh()` shortly after their action's own UI update. Explicitly harmless per the
finding itself (wasteful, not incorrect) — not routed as an action item.

**AD-12 — `SyncStatusIndicator` must mount/join the shared personal channel before other consumers for first-render status correctness; enforced only by incidental JSX order in `layout.tsx`, not a code contract.**
Same shape as the already-dropped EC-4: a fragile-but-currently-fine invariant. Low priority.

**AD-13 — `useBfcacheRefresh` and `useTripLiveRefresh`'s reconnect-resync can both fire `router.refresh()` independently for the same bfcache-restore cause**, doubling the RSC fetch for that one navigation. The generation-counter dedup `use-live-refresh.ts` built specifically to prevent this class of redundant refresh doesn't span the two separate hooks. Low severity (double-fetch, not corruption).

**AD-14 — first-load latency past the 2s grace window announces "Reconnecting" to screen readers even though the user never had a prior connection.** UX/copy nit on the shared connection-state machine.

#### edge-case-hunter (complete)

**EC-1 — `deleteTrip` purges the topic but never calls `stopHeartbeatSchedulerIfIdle()`.**
`purgeTripTopic` (`trip-events.ts:225-232`) clears and deletes the trip's topic directly, bypassing
the idle-check that every `unsubscribe()` closure calls. If a deleted trip's topic was the scheduler's
last reason to keep running, the heartbeat `setInterval` keeps ticking over now-empty maps until an
unrelated subscribe/unsubscribe elsewhere happens to re-check idleness. Low severity (self-heals on
the next unrelated event) but a real gap in the "no idle interval" guarantee the design notes claim.

**EC-2 — `removeTripSubscribersForUser` (force-revocation path) empties a Set without pruning the now-empty entry from `tripTopics`.**
Same shape as EC-1: `removeTripSubscribersForUser` (`trip-events.ts:210-223`) deletes subscribers from
the Set but doesn't delete the trip key from `tripTopics` when the Set becomes empty, unlike the
symmetric check inside the normal `unsubscribe()` closures (`subscribers.size === 0 && tripTopics.get(tripId) === subscribers`).
A revoked user's connection is the one path this exists for — so the exact removal that's supposed to
clean up can leave a stale empty entry ticked every heartbeat forever.

**EC-3 — the connect-time heartbeat flush in `createLiveSyncResponse` is the one enqueue with no guard.**
Every per-subscriber delivery in `trip-events.ts` is wrapped in try/catch ("one throwing callback
never blocks the rest"). The one-time synchronous flush on connect (`trip-events.ts:289`) is not — an
`enqueue` failure there escapes `ReadableStream.start()` unguarded, unlike every other frame delivery
in the same file.

**EC-4 — reconnect-resync can silently skip its own "prove you're really reconnected" edge when a channel is shared.**
When a `useLiveSync` consumer's target URL changes onto a channel another consumer already holds
`Connected`, `use-live-sync.ts:154` sets status directly from the existing channel's state rather than
forcing a `Reconnecting → Connected` transition — so a component relying on the transition edge itself
(rather than the terminal state) to trigger its "reconnect happened, do a full resync" logic could
miss it. Needs confirmation this dependency actually exists anywhere in the codebase (see Phase 4
routing below) — the finding is about a state-machine asymmetry, not a confirmed consumer bug yet.

**EC-5 — same client-side throw-isolation gap as VG-2, independently found**, this time pointing at
the dashboard/revocation-modal interaction specifically as the affected consumer chain
(`use-live-sync.ts:48,76`). Two lenses converging on the same root cause from different angles is
itself signal, not duplication — kept as a separate line per the skill's dedup rule.

**EC-6 — the trip page's own SSE channel (opened by `useTripLiveRefresh`, separate from the personal channel) isn't reflected in `SyncStatusIndicator`.**
`sync-status-indicator.tsx:128` reads only `useLiveSync()` against the personal `/api/users/me/events`
channel. On a trip page, `useTripLiveRefresh` opens a *second*, trip-scoped `EventSource`. If that
second channel degrades while the personal channel stays healthy, the indicator still reads
"Connected" — the epic's own UX-DR10 design intent ("the status bar is the single source of truth for
ambient connection state") isn't fully met on trip pages specifically, since the indicator can't see
the trip channel's health.

**EC-7 — dashboard-side dialogs (`TripEditSheet`, `NewTripDialog`) have no revocation-ticket subscription, unlike the trip page.**
`trips/[tripId]/page-client.tsx:139-153` subscribes to the revocation ticket and force-closes open
dialogs on self-targeted removal. The dashboard's own `page-client.tsx` has no equivalent — if a
manager has `TripEditSheet` open for a trip and is removed from it in the same session (e.g. a second
manager on that trip removes them), the edit sheet stays open with staged edits behind whatever the
app-shell revocation modal renders, rather than being discarded. Same shape as the trip-page problem
story 4.4 solved, on a surface 4.4/4.5 didn't cover — the dashboard-specific removal scenario (4.5's
own scope) only handles the trip *disappearing from the list*, not an *open dialog* for that trip.

## Behavior verification

Ran the full E2E coverage for all four epic-4 feature tags directly against a fresh dev server on
current `HEAD` (`npx playwright test --grep "@feat:revocation-modal|@feat:sync-status|@feat:trip-live-refresh|@feat:dashboard-live-sync"`,
bypassing `run-e2e.mjs`'s known Windows multi-tag `--grep` mis-split so all four tags could run in
one pass). This is a real Chromium browser driving the real dev server against the seeded `packt_e2e`
Postgres database — not a mock.

**11/11 passed, 56.9s:**

- `sync-status`: healthy connection shows nothing; dropped connection raises a reconnecting icon
  revealed on focus; tapping the problem icon reveals its label; a dead channel reports "cannot
  sync" and clears on recovery (the slowest scenario at 30.1s — it waits out the real heartbeat +
  dead-channel-grace timers rather than faking them)
- `dashboard-live-sync`: a contributor demoted to viewer loses dashboard edit access without a
  reload; a contributor removed while viewing the dashboard sees revocation and loses the trip
- `trip-live-refresh`: an itinerary edit in a second tab appears in the first tab without a reload
  (genuine two-tab/two-EventSource concurrent-session scenario); a contributor demoted to viewer
  loses the Budget tab on their open trip page
- `revocation-modal`: a contributor is removed while viewing the trip; a manager with staged
  share-dialog changes is removed (the force-close-dialogs path)

This directly exercises the two riskiest cross-story seams: the dead-channel/heartbeat watchdog
(story 4.2's state machine reacting to real timer expiry, now running through the post-epic
heartbeat-fanout fix's rewritten scheduler) and the revocation force-close-on-open-dialog interaction
(stories 4.4 × the share dialog). All observed behavior matched the declared acceptance criteria.
Passing E2E does not by itself prove the fan-out fix specifically (that requires simulating a
subscriber whose registration is missing from `tripTopics`/`userTopics`, which is a unit-level
scenario — see `trip-events.test.ts:258` per the spec's Suggested Review Order) — this run confirms
the happy-path and dead-channel-from-total-silence paths, not the "registered but silently dropped"
path the bugfix specifically targets.

**Process lessons (upstream prevention, not one-off fixes):**

- **Force-path/normal-path cleanup parity.** Item #1's root cause — a "fast path" (`removeTripSubscribersForUser`, `purgeTripTopic`) added as a sibling to the normal subscribe/unsubscribe closures, duplicating *some* of their cleanup but not all — is a recognizable shape: whenever a codebase adds a second way to reach the same end state as an existing lifecycle path, the two need either a shared implementation or a test asserting behavioral parity between them. Neither existed here. Worth a standing review-guidance line for future live-sync/subscription work in this codebase.
- **"Deferred to a later story" needs the later story's actual scope checked, not just its existence.** This is `epic-3-retro-item-15` recurring in a new shape: epic-3's action item was about verifying the later story *exists*; here the later stories (4.4, 4.5) did exist, but their declared scope never actually included the deferral (`use-trip-live-refresh.ts`/`use-dashboard-live-refresh.ts` comments say "those are 4.4/4.5 concerns" — neither story's AC says so). The lesson generalizes: a comment deferring work to a named future story should be checked against that story's actual AC at the point the story is written, not just trusted at the point the comment is written.
- **Duplication across near-identical files is a per-story review blind spot.** The SSE-route duplication (Findings section, Duplication map) went undetected for the whole epic because the two files never landed in the same story's diff. A retrospective-time or periodic structural-similarity check (even a simple `diff` between files that share an obvious naming pattern, like the two SSE routes) would have caught this mid-epic instead of needing a dedicated post-epic bugfix.
- **What worked, worth repeating:** the mid-epic self-correction on `use-trip-live-refresh.ts`/`use-dashboard-live-refresh.ts` duplication (extracted into `use-live-refresh.ts` during story 4.5, commit `c994e37`) shows the same failure mode *is* catchable within a story when the implementer happens to have both files in view. No process change needed here — just worth noting the epic didn't uniformly miss this class of issue.
