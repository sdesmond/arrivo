# Epic 3 Retrospective: Contributor Management Dialog

## Epic summary

Epic 3 gives a trip manager a single share dialog (`trip-share-dialog.tsx`) to administer every contributor, pending invitation, and declined invitation on a trip: staged batch role-change/removal applied atomically, immediate resend/rescind/dismiss on invitation rows, and an unsaved-changes guard blocking accidental Esc/backdrop dismissal. It retires `trip-edit-collaborators.tsx` / the `trip-edit-sheet.tsx` People section as the sole control plane.

**Stories:** 3.1 shell → 3.2 resend/rescind → 3.3 invite wiring + dead-surface removal → 3.4 dismiss declined → 3.5 batch save → 3.6 unsaved-changes guard. All six `done`; `pending_stories` empty (per `detect-epic --epic 3`).

**Diff range:** `119f647..8b79ba5` (24 commits, 7 merges). This range also contains an unrelated interleaved PR — the multi-user dev-seed rebuild (`cc992bb`…`9ed472b`, merged between stories 3.1 and 3.2) — which was excluded from all Phase 2 review scope; it touches `src/db/seed-data/**` and related dev tooling, not the share dialog.

**Evidence available:** epic spec (`epics-trip-contributors.md` §Epic 3), `epic-3-context.md`, all six story specs (all fully checked off, no open Review Finding checkboxes), `sprint-status.yaml`, the prior epic-2 retro, and the approved `sprint-change-proposal-2026-09-03.md` that added story 3.3. **Not available:** session logs for individual story-implementation conversations (process-lesson analysis below is drawn from the specs' own Spec Change Log / Review sections instead, where they record renegotiations and in-story fixes).

**Note on `git_evidence.py` attribution:** the script's per-commit `stories` field returned empty for every commit in range — commit subjects use natural-language descriptions ("feat: guard staged contributor changes...") rather than the story-id slugs the matcher expects. Per-story commit grouping in this document was done manually from PR merge order and each spec's `baseline_commit`, cross-checked and confirmed consistent.

## Findings

### Correctness (adversarial / edge-case lenses + direct verification)

1. **Staged-removal rows stay fully interactive.** A collaborator staged for removal renders at `opacity: 0.5` with a "Will be removed on Save" caption, but `TripShareCollaboratorRow` still receives live `onRemove`/`onRoleChange` callbacks — no `disabled` state is threaded through. Opening the role dropdown on an already-removal-staged row silently overwrites the staged `remove` entry with a `role` change (both key off the same `collaboratorId` in `stagedChanges`), un-staging the removal with no confirmation and no test coverage for the transition.
   `src/components/packt/trip-share-dialog.tsx` (collaborator row-map block) — confirmed independently by both the edge-case and adversarial lenses and by direct read.
   **Disposition:** fixed — `TripShareCollaboratorRow` now takes a `disabled` prop, wired from `pendingRemoval` at the call site (branch `fix/epic-3-retro-followups`). **Process lesson:** story 3.5's design didn't consider the interaction between two staged-change *types* on the same row; a review pass that asks "does this new staged-state also need to suppress the controls that produced the *other* staged state" would catch this class.

2. **`saveContributorChanges` doesn't reuse the guard it was supposed to.** Story 3.5's own spec checklist claims the extracted `assertNotCreator` helper is reused in `removeCollaborator`/`updateCollaboratorRole`/`saveContributorChanges` (spec-3-5 line 59, checked `[x]`), but `saveContributorChanges` actually reimplements the same isCreator check inline via `ContributorChangeGuardError` (`src/app/(app)/trips/actions.ts:1030`). `assertNotCreator` (`:940`) is used only at `:951` and `:961` — the two legacy actions that are now dead code (finding 3).
   **Disposition:** fixed — `assertNotCreator` now takes an optional `ErrorClass` (defaulting to `Error`); `saveContributorChanges` calls it with `ContributorChangeGuardError` instead of duplicating the check (branch `fix/epic-3-retro-followups`). **Process lesson:** this is exactly the scenario epic-2-retro-item-6 tried to prevent ("fold before 3.5 adds a third call site"); a spec checklist item that claims N call sites reuse a helper should be verified by grepping for the helper's actual call count, not just marked done because the helper exists.

3. **Dead legacy actions.** `addCollaborator`/`removeCollaborator`/`updateCollaboratorRole` in `src/app/(app)/trips/actions.ts` have zero production callers since story 3.3 deleted `trip-edit-collaborators.tsx` (their only caller) — confirmed by grep across `src/components`. They remain exported and fully unit-tested, which hides them from any dead-code signal.
   **Disposition:** fixed — `addCollaborator`/`removeCollaborator`/`updateCollaboratorRole` and their tests deleted, along with the now-orphaned `AddCollaboratorInput` type (branch `fix/epic-3-retro-followups`). **Process lesson:** story 3.3's scope ("remove dead collaborator surfaces") stopped at the UI layer; a component-deletion story should also grep for now-orphaned server actions the deleted component was the sole caller of.

4. **No self-row affordance in the dialog.** `Collaborator.userId` is never populated or threaded into the dialog (confirmed: no `currentUserId`/session reference anywhere in `trip-share-dialog.tsx`), so the manager's own row renders with a fully live role dropdown and remove button — only the creator's row is locked. Staging a change to your own row reaches Save, which rejects the *whole batch* with a generic "You cannot change your own access" message; because this rejection has `stale: false`, `stagedChanges` is never cleared (`handleSaveChanges` only resets staged state on the `stale` branch, `:100-101`), but there's also no way to tell which staged row was the offender.
   **Disposition:** fix now, or accept-as-is if judged low-frequency — recommend at minimum identifying the offending row in the error state. **Process lesson:** every other server-side "can't touch X" rule in this epic (creator row) got a paired UI affordance; the self-row rule didn't. Spec review should pair each server-side hard rule with an explicit "does the UI need to reflect this" question.

5. **Missing E2E for the epic's headline flow.** `sprint-change-proposal-2026-09-03.md` (the change that created story 3.3, because "the feature's primary use case — inviting a collaborator — is broken") explicitly required updating `tests/e2e/features/trip-sharing.feature` + steps for "manager enters email, clicks Invite, sees new contributor in list" (line 74). Story 3.3's actual spec scoped verification to component tests only (`trip-share-dialog.test.tsx`, spec-3-3 lines 59-84); `trip-sharing.feature` has zero invite-related scenarios (`grep -i invite` returns nothing). The invite flow's only coverage mocks the server action, so nothing verifies the real round trip (server action → DB → refetch) end to end.
   **Disposition:** fix now — add the E2E scenario the approved change proposal specified. **Process lesson:** an approved sprint-change-proposal's deliverable list should be diffed against the eventual story's "Files & Tests" section before the story is marked done, not assumed satisfied because *a* test exists.

6. **`getShareDialogData` wrapper is untested.** Its four sibling wrappers in the same file (`resendShareInvitation`, `rescindShareInvitation`, `dismissShareInvitation`, `saveContributorChanges`) each have a call-forwarding test in `actions.test.ts` asserting the delegate receives the right `(tripId, userId)` pair; `getShareDialogData` has none, and both consumer test files mock it away wholesale. A caller-side argument bug (e.g. swapped `tripId`/`userId`) would break the real manager-only sharing gate while every existing test still passes. (Verification-gap lens finding, confirmed via grep.)
   **Disposition:** fixed — added `getShareDialogData` call-forwarding tests (success + rejection) mirroring the sibling pattern (branch `fix/epic-3-retro-followups`).

7. **`rescindPendingInvitation` doesn't track dismissal like `dismissDeclinedInvitation` does.** Only `dismissDeclinedInvitation` adds to `dismissedInvitationIdsRef` (`:243`), which the invite- and stale-save-recovery refetches consult to avoid resurrecting a just-removed row (`:107`, `:160`). Rescind does the equivalent local-state filtering but never populates the ref — confirmed by grep (3 of 4 uses are read sites, only 1 write site, from dismiss).
   **Disposition:** defer. Narrow race (requires a rescind and an invite/stale-save-refetch to overlap); same pattern 3.4 solved for dismiss should extend to rescind for consistency.

8. **Expired-but-still-`pending` invitations are a dead end in the dialog.** `getContributorsAndInvitations`'s WHERE clause excludes any `status='pending'` row whose `expiresAt` has passed (`queries.ts:359-374`); `dismissInvitation`'s guard separately refuses anything with `status='pending'` regardless of expiry (`ne(invitations.status, "pending")`). The only way such a row's state changes is a manager re-inviting the *exact* same email (which silently reuses/extends it via `applyInvitationResend`). A manager has no way to see or clean up these ghost rows through the dialog.
   **Disposition:** defer — this is inherited behavior (story 3.1 explicitly matches "the dashboard's own expiry filter, Story 1.4"), not a regression this epic introduced; worth a small follow-up story letting managers dismiss expired-pending rows specifically.

9. **Two narrow concurrency races**, both low-likelihood: (a) staging an edit on a *different* row while a save is in flight is silently dropped, since `handleSaveChanges`'s success branch unconditionally clears `stagedChanges` (`:117`) with no guard against new staging that happened mid-request; (b) the invite form isn't disabled during `isSavingChanges` (`TripShareInviteForm`'s `isLoading` binds only to `inviteLoading`), so an invite and a save's stale-recovery refetch can race and clobber each other's freshly-fetched `data`.
   **Disposition:** defer — both require the user to act on the dialog within a live request's round trip; track but don't block on.

10. **Minor:** `handleSaveChanges`'s stale-recovery refetch has an empty `catch` (`:111-113`) — if the network issue causing the stale rejection also breaks the recovery refetch, the user sees only the original error text with no signal that the automatic refresh also failed.
    **Disposition:** defer, low severity.

11. **Minor style:** `src/app/(app)/trips/[tripId]/actions.ts:81` uses an inline `import("@/data/types").ContributorChange[]` type expression instead of the project's standard top-level type import.
    **Disposition:** defer, trivial cleanup.

### Findings investigated and rejected (recorded so they aren't re-flagged)

12. *Adversarial lens claimed the X button bypasses the 3.6 unsaved-changes guard, contradicting its intent.* **Rejected** — verified against spec-3-6, which explicitly documents this as deliberate, human-renegotiated design (2026-09-03 Spec Change Log entry): only Esc/backdrop-click are blocked; Save, Cancel, and the X button all close the dialog (X and Cancel discard silently, matching pre-3.6 behavior). The X button *not* prompting for confirmation is the spec, not a gap.

13. *Edge-case lens raised an `invitation.status === 'expired'` scenario as unhandled.* **Rejected as out-of-epic-scope** — grepped the codebase; no code path ever writes `status='expired'` to a row. The enum value (`InvitationStatus.Expired`, `types.ts:45`) is a pre-existing, apparently-unused member from Epic 1's data model, untouched by this epic's diff.

14. *Edge-case lens raised duplicate declined+pending rows on re-invite.* **Rejected** — verified `inviteContributor` already deletes the prior declined row before inserting the new pending one (`actions.ts` ~738-747).

This is an **accepted deviation** (each story consistently chose to extend the existing action files rather than split), but the architecture note is now stale.

## Acceptance verdict

**accepted-with-open-items** (criteria declared, in `epics-trip-contributors.md` §Epic 3 and `epic-3-context.md`).

All six stories are `done`, `pending_stories` is empty, and the epic's core promise holds: a manager can view every contributor/pending/declined row from one dialog, resend/rescind/dismiss act immediately, role/removal edits stage and save as one atomic batch, and Esc/backdrop-click are unconditional no-ops. No finding above breaks any of those paths in normal use. The correctness bug (finding 1), the guard-duplication gap (finding 2), and the dead legacy code (finding 3) were fixed within this retrospective (branch `fix/epic-3-retro-followups`, validated clean). What remains open is a missing E2E scenario for the invite flow that already has component coverage (finding 5) and several low-likelihood edge cases (findings 4, 7-11) — none of which reopens a story or blocks the epic from standing as delivered.
