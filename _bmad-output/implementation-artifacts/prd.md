# Product Requirements Document - Packt

**Author:** Spencer
**Date:** 2026-05-31

## Executive Summary

Packt is adding a packing list feature to its travel itinerary planning application. The feature addresses a specific preparation failure mode: the asymmetric cost of forgotten items — a missing passport ends a trip, missing socks costs ten dollars. Current workarounds (notes apps, paper lists, memory) are disconnected from the trip planning context and rebuilt from scratch for every trip.

Target users are existing Packt users planning multi-day trips. The feature lives on a dedicated Packing tab within each trip, anchoring packing to the planning workflow rather than treating it as an afterthought.

### What Makes This Special

The feature is a two-layer system: a personal template library of named, user-owned item collections ("Business Trip," "Beach Holiday," "Winter Ski") and per-trip packing lists generated by pulling and merging those templates with automatic deduplication. Items are plain text — no types, categories, or quantity metadata. The user's own language is the right schema.

The template library becomes accumulated travel expertise. Each named template is the user's personal answer to a recurring trip type, refined over multiple trips. New trips start from that earned baseline rather than from scratch. Templates stay clean and reusable; the trip list is stateful, fully editable, and non-destructive to its sources.

Phase 1 delivers the structural foundation. Phase 2 intelligence (weather-conditional items, passport expiry detection, location-aware suggestions) is explicitly deferred but architecturally anticipated — the data model accommodates it without requiring it.

## Project Classification

- **Project Type:** Web Application (Next.js App Router, browser-based)
- **Domain:** General — travel productivity; no regulatory or compliance concerns
- **Complexity:** Low — established UI patterns, no novel technical risks, all dependencies already in place
- **Project Context:** Brownfield — feature addition to an existing production application; packing tab already stubbed, three server actions exist (`addPackingItem`, `togglePackingItem`, `removePackingItem`), `@dnd-kit` already installed

## Success Criteria

### User Success

The feature succeeds when users engage heavily with packing in the days before departure and think about it zero times once they're traveling. The list did its job when it disappears from working memory entirely after takeoff.

Specific indicators:
- A user can pull a template and have a trip-ready packing list in under 60 seconds
- Returning users don't rebuild from scratch — they pull a previously-built template and adjust
- Users arrive at their destination having forgotten nothing on their list; the list reflects their actual travel needs without post-hoc additions
- The template library grows over time — a user's second trip of a given type starts from a better baseline than their first

### Business Success

The app is in active development with no production user base yet. Success at launch is establishing that the feature is used and useful — confirmed through real usage patterns rather than predefined thresholds. The signal is engagement before departure (list creation, item checks) paired with the absence of abandoned or empty lists.

### Technical Success

- Packing state persists correctly across sessions; a user who partially packs, closes the app, and returns sees exactly where they left off
- No regressions in existing trip and itinerary functionality
- Full E2E coverage of all Phase 1 flows passing in CI
- Template pull with deduplication produces the correct merged list every time
- Progress indicator on trip cards reflects live checked/total counts

## Product Scope

### MVP — Minimum Viable Product

All 7 Phase 1 features ship as a single coherent release. The Packing tab is pre-departure only — intentionally distinct from itinerary inline checklists, which handle in-trip execution. These serve different temporal contexts and mental modes and must not be conflated.

1. **Template library** — create, rename, delete named templates; add, edit, remove items and section labels within each template
2. **Trip packing tab** — empty state with prompt to pull a template; pull one or more templates with automatic deduplication (silent, with lightweight "X duplicates skipped" notice)
3. **Flat list with section labels** — items and labels as siblings in a flat array; labels are non-checkable, tap to rename or delete; label strikethrough when all items beneath it are checked (client-side derived state)
4. **Check/uncheck items** — persisted state; survives page reload and session close
5. **Drag-to-reorder items** — items only (not labels) in Phase 1; position persists
6. **Append template to existing list** — apply additional templates after initial creation; duplicates silently skipped
7. **Save trip list as template** — save the current trip list as a named template for future use; closes the library loop

### Growth Features (Post-MVP)

- Cherry-pick individual items from a template instead of pulling all-or-nothing
- Section drag — move an entire section as a group
- Multiple named lists per trip (e.g., "Spencer's packing," "Kids' packing," "Day Hike gear")
- Event-attached lists — attach a named list to an itinerary event, visible inline

### Vision (Future)

- Smart suggestions: passport expiry detection against trip dates, weather-conditional items (surfaced closer to departure), destination-aware adapter and visa prompts
- Time-staged reminders: surface weather-sensitive items 5–7 days before departure rather than at list creation
- Collaborative packing: per-collaborator lists within a shared trip

## User Journeys

### Journey 1: First Packing List (No Templates Yet)

Spencer just added a two-week trip to Japan to Packt. He clicks the Packing tab and sees an empty state: no list, no templates. A prompt says "Build a packing list — start from scratch or create a template to reuse." He chooses to start from scratch, adding items as they come to him: "Passport," "Laptop," "USB-C charger," "Rain jacket." He adds a "Documents" section label and moves Passport under it. Halfway through, he notices he's building something he'll need again — everything here is his standard international kit. He finishes the list, then saves it as a template: "International Trip." The list took 8 minutes to build once. It will never take 8 minutes again.

*Requirements revealed: empty state → free-form item entry, section label creation, add-item flow, save-as-template action.*

### Journey 2: Routine Trip — Template Pull

Three months later, Spencer adds a weekend city break to London. He opens the Packing tab. This time it's different — he pulls "City Break" from his template library. Eighteen items populate instantly. He scans the list: looks right. He adds "formal shoes" (he's attending a dinner), removes "hiking boots" (not that kind of trip). Ninety seconds start to finish. He closes the app and doesn't think about packing again until he's standing in front of his open suitcase.

*Requirements revealed: pull template UI, deduplication notice (not triggered here), inline add/remove from existing list.*

### Journey 3: Pre-Departure Packing Across Sessions

Two days before departure, Spencer opens Packt on his phone. Bag is open on the floor. He starts working through the list — checkmarks as items go in. He gets through 12 of 18 items, then has to stop to take a call. He closes the app. That evening he reopens it: 12 of 18, exactly where he left off. He finishes the last 6 the next morning. The trip card now shows "18 / 18 packed." That number is the last packing-related thought he has before takeoff.

*Requirements revealed: persisted check state across sessions, progress counter on trip card, resume-from-partial-state.*

### Journey 4: Merging Templates — Edge Case

Spencer is going on a ski trip to Austria — international travel plus ski-specific gear. He pulls both "International Trip" and "Winter Ski" templates. A quiet notice appears: "2 items skipped (duplicates)." The merged list has 26 items. He scans it, adds "ski boot bag," removes "laptop" (vacation, leaving it at home). After the trip, he realizes this merged list is exactly right for international ski trips. He saves it as a new template: "International Ski." His library now has four templates, each earned rather than invented.

*Requirements revealed: multi-template pull, deduplication with lightweight notice, save-as-template from merged list, template naming.*

## Web App Specific Requirements

### Project-Type Overview

Packt is a Next.js App Router application using the established server component / client component split pattern: `page.tsx` handles server-side data fetching and auth; `page-client.tsx` handles interactive UI. The packing feature follows this same pattern throughout. All packing state mutations go through server actions with `revalidatePath` for cache invalidation — no real-time sync in Phase 1.

### Browser Matrix

Target: modern evergreen browsers — Chrome, Safari, Firefox, Edge (current and previous major release). No IE11, no legacy mobile browser support required.

### Responsive Design

The packing tab must work well at all viewport sizes. Expected usage patterns span desktop trip planning (building templates, pulling templates) and mobile on-the-go packing (checking items off). The list UI, drag handles, and inline editing must be fully usable on touch screens.

### SEO

Not applicable — packing feature is behind authentication.

### Implementation Considerations

- `"use client"` at the top of all interactive packing components
- Drag-to-reorder uses `@dnd-kit/core` + `@dnd-kit/sortable` (already installed, already used for event reordering — reuse patterns from existing drag implementation)
- Server actions follow the existing `requireUser()` + `assertTripAccess()` + `revalidatePath()` pattern
- All new types added to `src/data/types.ts` — no local type definitions

## Project Scoping

### Strategy & Philosophy

**Approach:** Experience MVP — all 7 Phase 1 features ship as a single coherent release. The features are interdependent: a template library with no packing tab to pull into is useless; check/uncheck without persistence is meaningless; the progress indicator is only motivating once the checklist works. Shipping them together is the minimum that delivers the complete experience.

**Resource Requirements:** Solo developer, no external deadline. Timeline is effort-driven, not calendar-driven.

### Risk Mitigation Strategy

**Technical Risks:** Keyboard accessibility for drag-to-reorder is the only notable open question. Mitigated by `@dnd-kit`'s built-in keyboard support; assumed solved through correct library usage. No novel technical risks — all dependencies installed, patterns established.

**Market Risks:** App is in active development, no production user base yet. No adoption pressure or launch deadline. Risk profile is low.

**Resource Risks:** Solo developer mitigates coordination overhead. Scope is well-bounded with clear feature boundaries. If scope pressure arises, Phase 2 features (cherry-pick, section drag, multi-list) are cleanly separable with no Phase 1 entanglement.

## Functional Requirements

### Template Library Management

- **FR1:** User can create a new named packing template
- **FR2:** User can rename an existing template
- **FR3:** User can delete a template
- **FR4:** User can view all their packing templates
- **FR5:** User can add a plain-text item to a template
- **FR6:** User can edit the text of an item in a template
- **FR7:** User can remove an item from a template
- **FR8:** User can add a section label to a template
- **FR9:** User can rename a section label in a template
- **FR10:** User can delete a section label from a template, leaving its items ungrouped
- **FR11:** User can reorder items within a template

### Trip Packing List

- **FR12:** User can view a dedicated Packing tab within a trip
- **FR13:** User sees an empty state with actionable prompts when no packing list exists for a trip
- **FR14:** User can pull one or more templates onto a trip's packing list
- **FR15:** System automatically deduplicates items when pulling templates, with a lightweight count notice
- **FR16:** User can pull additional templates onto an already-populated packing list
- **FR17:** User can add a plain-text item to a trip packing list
- **FR18:** User can add a section label to a trip packing list
- **FR19:** User can remove an item or section label from a trip packing list
- **FR20:** User can save a trip's current packing list as a new named template

### List Structure

- **FR21:** Items and section labels coexist as siblings in a flat array with no nesting
- **FR22:** Section labels are visually distinct and non-interactive as checkboxes
- **FR23:** Items not under any section label appear at the bottom of the list, below all sections
- **FR24:** A section label displays a strikethrough state when all items beneath it are checked
- **FR25:** Items can be added contextually under a specific section or to the ungrouped bottom area

### List Interaction

- **FR26:** User can check an item as packed
- **FR27:** User can uncheck a previously checked item
- **FR28:** Check state persists across browser sessions and page reloads
- **FR29:** User can drag an item to a new position in the list
- **FR30:** User can reorder an item via keyboard controls without using drag
- **FR31:** Item positions persist across browser sessions and page reloads
- **FR32:** User can edit the text of an existing item inline
- **FR33:** User can tap or click a section label to rename it inline
- **FR34:** User can delete a section label via its inline edit controls

### Trip Overview Integration

- **FR35:** Trip card displays a packing progress count showing checked items vs total checkable items
- **FR36:** Progress count updates when items are checked or unchecked
- **FR37:** Progress count reflects only checkable items, not section labels

## Non-Functional Requirements

### Performance

- **NFR1:** All user-initiated packing interactions (check/uncheck, add item, remove item, inline edit) complete within 300ms p95 as perceived by the user
- **NFR2:** Template pull with deduplication for lists up to 200 items completes within 500ms
- **NFR3:** Drag-to-reorder renders at 60fps during active drag with no visible frame drops
- **NFR4:** Packing tab initial render (with list populated) completes within 2 seconds on a standard broadband connection

### Security

- **NFR5:** Packing data (templates and trip lists) is accessible only to the authenticated user who owns it
- **NFR6:** All server actions validate user authentication and trip access before reading or writing any packing data — no action bypasses `requireUser()` + `assertTripAccess()`
- **NFR7:** Template data is strictly user-scoped — no user can read, modify, or enumerate another user's templates

### Accessibility

- **NFR8:** All packing features meet WCAG 2.1 AA compliance
- **NFR9:** Drag-to-reorder provides a keyboard-accessible alternative (move up/down) for users who cannot use mouse or touch drag
- **NFR10:** All interactive elements have a visible focus indicator meeting WCAG 2.1 AA contrast requirements
- **NFR11:** Check state changes are announced to screen readers via appropriate ARIA attributes
- **NFR12:** All touch targets for interactive elements are at minimum 44×44px on mobile viewports
