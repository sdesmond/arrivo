## Findings

### Process — Story 1.1 shipped without a PR review checkpoint

Stories 1.2, 1.3, and 1.4 each landed through a dedicated PR (#248, #249, #250 — confirmed via `gh pr list`), each with a `## Summary` / `## Test plan` body. Story 1.1 — the role-rename-plus-data-backfill story, the one every later story and every future epic depends on for `assertTripAccess` ranking — has no corresponding PR at all: commit `83c75df` ("feat: separate trip creator from collaborator authority") sits directly on `feat/trip-sharing` with no merge commit around it. It is also the highest-risk story in the epic (one-off backfill script + auth-rank change touching every trip-access call site), yet it is the one story that bypassed the review checkpoint the other three went through.

- **Source:** `git log 46b5bb6..a3c146a` (commit `83c75dff2725e9f0de543187f27c13197836942f`, no adjoining merge); `gh pr list` (PRs #248/#249/#250 exist for 1.2–1.4, none for 1.1).
- **Disposition:** accept as-is (nothing to remediate retroactively — the code itself was reviewed via the plan-approval/spec-review gates and passed validation per its own Verification section). **Process lesson:** the dev workflow should guarantee every story opens a PR, including the first story on a fresh feature branch.

### Reconciliation gap — dead "Add person" collaborator editor now contradicts the new invite-only model

`TripEditSheet`'s "People" section (`src/components/packt/trip-edit-collaborators.tsx:96-129`) still renders a live "Add person" form (name + email + role + Add button) plus per-row Remove buttons and role selects. All three handlers (`onAdd`, `onRemove`, `onUpdateRole`, wired in `src/components/packt/trip-edit-sheet.tsx:98-128`) mutate only the drawer's local `draft` state. `getPatch()` (`trip-edit-sheet.tsx:149-177`), which builds the payload actually sent to `onSave`/`updateTripMetadata`, never includes a `collaborators` field — and `UpdateTripPatch` (`src/data/types.ts:747-760`) has no such field to carry it. This predates Epic 1 (confirmed via `git log -p --follow` on the file: `collaborators` never appears in the returned patch object in any prior revision), so the epic did not introduce it. But Story 1.1 touched this exact file to relabel `"owner"` → `"manager"` without flagging that the whole editor is inert, and the epic as a whole just shipped a real, working, invite-based collaborator flow that this dead widget now visually contradicts.

- **Failure scenario:** A manager opens Edit Trip → People, types a real Packt user's name and email into "Add person," clicks Add, sees the person appear in the list, clicks Save. The drawer closes; on reopen the person is gone. No invitation was ever created, no error was shown — the manager reasonably believes they granted access and did not. The same applies in reverse: removing or re-roling an existing collaborator via this drawer silently reverts on next open.
- **Source:** `src/components/packt/trip-edit-sheet.tsx:149-193`, `src/components/packt/trip-edit-collaborators.tsx:96-129`, `src/data/types.ts:747-760`.
- **Disposition:** fix-now candidate, routed as an action item rather than fixed here (out of this epic's own story scope, and Epic 3's share dialog — Story 3.1 — is the more likely permanent home for this UI). Until Epic 3 ships, this widget should not be left silently misleading.

### Deferred item not picked up — no supporting index for the pending-invitations email lookup

Story 1.2's own `deferred-work.md` entry asked for "an index on `invitations.email` alone," anticipating Story 1.3's `getMyPendingInvitations` lookup. Story 1.3 shipped that lookup (`src/lib/invitations.ts:30-52`) but the deferred item was never picked up — `src/db/schema.ts:268-291` still defines only `invitations_pending_trip_email_unique`, a partial unique index on `(tripId, email)` WHERE `status='pending'`, which does not serve an email-only lookup. Separately, the deferred item as worded would not have been sufficient anyway: the actual query filters through `hasNormalizedEmail(invitations.email, ...)`, a `lower(trim(email))` SQL expression (`src/lib/invitations.ts:22-24`), which a plain btree index on raw `email` cannot serve — it needs an expression index on `lower(trim(email))`.

- **Source:** `_bmad-output/implementation-artifacts/deferred-work.md`; `src/db/schema.ts:268-291`; `src/lib/invitations.ts:22-52`.
- **Disposition:** defer. Low severity at current scale (small personal-travel-app user counts), but the deferred-work entry should be corrected to name the right fix before someone implements the wrong one.

### Minor — NavItem's badge aria-label hardcodes invitation-specific copy

`NavItem` (`src/components/packt/nav-item.tsx:16-18`) exposes generic `count`/`countTint` props but bakes `"{label}, {count} pending invitations"` into the aria-label unconditionally. Today `count` is wired only to the Trips item for the invitation badge (`src/components/packt/sidebar-nav.tsx:83-84`), so there is no live bug. But the component itself is now a trap: the next feature that reuses `NavItem.count` for an unrelated badge (e.g., unread messages) inherits a wrong, misleading aria-label with nothing in the type system or tests to catch it.

- **Source:** `src/components/packt/nav-item.tsx:16-18`; `src/components/packt/sidebar-nav.tsx:83-84`.
- **Disposition:** defer — cheap to fix when a second badge actually shows up, not worth doing preemptively.

### Confirmed working — atomic invitation state transitions and defensive design match the architecture decisions

- `acceptInvitation`, `declineInvitation`, and `rescindInvitation` (`src/app/(app)/trips/actions.ts:797-914`) each use a single conditional `UPDATE ... WHERE id = ? AND status = 'pending' AND ... RETURNING`, never read-then-write, exactly as `epic-1-context.md`'s Technical Decisions section specifies — verified directly in the code, not just asserted by it.
- Email normalization (`normalizeEmail`, `hasNormalizedEmail`) is applied consistently across every invite/accept/decline/rescind/query path (`src/lib/invitations.ts`, `src/app/(app)/trips/actions.ts`).
- The Epic 4 (SSE live-sync) dependency called out in the epic context is correctly deferred with in-code `TODO(epic-4)` markers at the exact points the pub-sub calls will go (`actions.ts:848-849`, `:882-883`, `:908-910`), rather than silently skipped or half-built.
- Testing-pyramid discipline held: `rescindInvitation` has no UI caller yet (ships in Epic 3 Story 3.2 per its PR body), so it got unit coverage only and correctly no E2E — matching this project's "no duplication across layers" rule.
- `tests/e2e/features/pending-invitations.feature` covers accept-redirect, decline+toast+row-removal, badge-count-shown, badge-hidden-at-zero, expired-invitation-exclusion, and cross-user isolation — a 1:1 match to every UX behavior line in `epic-1-context.md`'s UX & Interaction Patterns section.
