# Accessibility Review — Packt (Reservations & Trip Logistics)

## Overall verdict

The spine pair is largely accessibility-sound: it deliberately reuses Packt's existing WCAG-conformant token pairs, the revised "Linked" indicator is genuinely dual-signaled (icon + badge), and the Accessibility Floor section in EXPERIENCE.md explicitly calls out tap targets, focus rings, and `title` attributes. The remaining gaps are mostly omissions rather than wrong choices: the "Linked" badge's `var(--fg-3)` foreground likely fails contrast on `var(--surface-2)`, several new interactive elements (chips, accordion previews, doc-row chevrons) lack explicit keyboard/focus and screen-reader semantics, the FR-9 banner's combined navigate+auto-open behavior isn't reconciled with WCAG 3.2.2, and the drawer's required/optional field distinction relies on color/text that should be reinforced with `aria-required`. None of these are deep structural problems — most fixes are additive notes to existing sections.

## Findings

### 1. Color contrast

- **high** — The "Linked" badge is specified with `var(--fg-3)` text on `var(--surface-2)` background (DESIGN.md `components.linked-event-badge`, line ~84-88; confirmed in `.working/key-itinerary-linked-event.html` `.linked-badge` rule, lines 245-256: `background: var(--surface-2); color: var(--fg-3);`). `--fg-3` is `#7a7a72` and `--surface-2` is `#efefec` — contrast ratio is approximately 3.5:1, below the 4.5:1 AA threshold for normal text (the badge text is 10px, which is "small text" under WCAG, requiring 4.5:1, not the 3:1 large-text minimum). DESIGN.md itself flags this as unresolved ("a slightly lighter `var(--fg-3)` foreground was used in the approved mock... no new badge variant is strictly required"). _Fix:_ Use `var(--fg-2)` (#4a4a45 on #efefec ≈ 8.4:1) for the badge foreground instead of `var(--fg-3)`, matching the actual `Badge` `muted`/`secondary` variant pairing (`[background:var(--surface-2)] [color:var(--fg-2)]`) that DESIGN.md says it's reusing. This also resolves the DESIGN.md vs. mock inconsistency — pick `--fg-2` and update both.

- **medium** — Reservation row anchor labels use `var(--fg-3)` on `var(--bg)` (white #ffffff): #7a7a72 on #ffffff ≈ 4.5:1 — passes AA for normal text but only barely, and at 13px (`--fs-card-sub`) this is borderline for users with low vision who increase `--font-scale` (font-scale doesn't fix contrast). _Fix:_ No change strictly required (it passes AA), but flag this as a "don't go lower than fg-3" floor — do not let any future iteration drop anchor labels to `--fg-4` (#a0a098 on white ≈ 2.3:1, fails AA entirely).

- **medium** — FR-9 banner description text (`.cta-description`, `var(--fg-3)` at 12.5px) sits on `var(--surface)` (#f6f6f4): #7a7a72 on #f6f6f4 ≈ 4.3:1 — fails the 4.5:1 AA threshold for small text by a small margin. _Fix:_ Bump banner description color to `var(--fg-2)` (#4a4a45 on #f6f6f4 ≈ 8.6:1), consistent with how `--fg-2` is used for "secondary labels" per DESIGN.md's own color-ramp description (line 126).

- **low** — Accordion collapsed-preview text mixes `var(--fg-2)` (provider name) and `var(--fg-3)` (rest of the line) on `var(--surface)` background (DESIGN.md line 200, mock `.accordion-preview`). The `--fg-3)` portion on `--surface` is the same ≈4.3:1 borderline case as the FR-9 banner description above. _Fix:_ Same as above — either accept (it's existing precedent in `day-card.tsx` if that pattern is already shipped) or bump to `--fg-2`. Worth a single consistent decision across both findings rather than two separate token choices.

### 2. Color-as-sole-signal

- **low** — The Linked Event indicator itself is well-handled: EXPERIENCE.md's Accessibility Floor (lines 96-101, 96 specifically) explicitly states the icon-swap and badge are redundant signals, neither relying on color alone. This is correctly implemented per the Do's/Don'ts table and the rejected violet-token history (decision log lines 16, 130). No finding here beyond the contrast issue in §1.

- **medium** — The "happening now" + Linked co-occurrence case: DESIGN.md (line 123) and EXPERIENCE.md confirm a Linked Event that is also "now" gets the same `--accent-soft`/"Now" pill treatment as any event — good, no new accent. However, neither spine states what happens to the "Linked" badge's *visual legibility* when the row background changes to `--accent-soft` (#d6efec). The badge background `var(--surface-2)` (#efefec) on top of `var(--accent-soft)` (#d6efec) row background is a near-identical light-on-light pairing — contrast between badge and its now-tinted surroundings could collapse to near-invisible, and combined with the §1 fg-3 contrast issue, the badge text could become unreadable in the "now + linked" case specifically. _Fix:_ Add a sentence to DESIGN.md's Linked Event component section confirming the "Linked" badge keeps its `--surface-2`/`--fg-2` (per fix above) styling unchanged when the row is also `now-row` — i.e., verify the combination visually, since `--surface-2` and `--accent-soft` are both very light.

### 3. Tap targets

- **low** — All explicitly-dimensioned new targets meet the `h-8`/32px floor: FR-9 dismiss (`size-8`, DESIGN.md line 103, mock line 171 `width: 32px; height: 32px`), inline doc-upload (EXPERIENCE.md line 98 explicitly raises the mock's 28px to `size-8`/32px), Add Reservation button (`h-10`), FR-9 CTA button (`h-9`). Good — this is correctly called out.

- **medium** — Accordion header (DESIGN.md line 198, mock `.accordion-header { padding: 12px 16px; }`) — the header is clickable as a whole (per EXPERIENCE.md "Click header to toggle"), and with `12px` vertical padding plus the `~18px` icon/text content, the total clickable height is roughly 12+12+18 = ~42px, comfortably above 32px. No issue, but the **chevron itself** (`14px`, DESIGN.md line 198) is not independently specified as a button — confirm it's not a separately-focusable/clickable element with its own (sub-32px) hit area; if the whole header `<button>` wraps it (as stated for keyboard operability, EXPERIENCE.md line 100), this is fine. _Fix:_ Add one clarifying sentence: "the chevron is decorative and not independently interactive — the entire header row is the single `<button>` target."

- **medium** — Reservation row click-to-edit fields (DESIGN.md line 217, EXPERIENCE.md line 57/84): "click text → input with `border-bottom: 1px solid var(--accent-brand)`". The clickable *text* (e.g., a single anchor-line value at 13px line-height) has no specified minimum hit-box — text-only click targets at 13px font-size produce a hit area well under 32px tall. _Fix:_ Specify that each click-to-edit field's clickable region extends to at least `min-height: 32px` (e.g., via padding or a wrapping element), even though the visible text is smaller — matching the `doc-row.tsx` precedent this pattern claims to follow (verify `doc-row.tsx` already does this; if so, just cite it explicitly here).

- **low** — Cover Overflow trigger is `34px × 34px` in the mock (`.overflow-trigger`, key-cover-overflow-menu.html line 157-158) vs. DESIGN.md's stated `size-9`-equivalent — actually 34px is between `size-8` (32px) and `size-9` (36px). This matches `now-card.tsx`'s existing trigger per the "direct reuse" instruction, so likely fine, but DESIGN.md doesn't state the exact px — it just says "reuse `now-card.tsx`'s pattern verbatim." _Fix:_ No action needed if `now-card.tsx` already uses 34px (verify against that file); otherwise round to `size-9` (36px) for token consistency.

### 4. Icon-only controls

- **low** — All four icon-only controls called out in EXPERIENCE.md's Accessibility Floor (doc-upload `title="Add document"`, FR-9 dismiss `title="Dismiss"`, Cover Overflow `title="Cover options"`) have explicit `title`s, and the mocks confirm (`key-itinerary-empty-cta-banner.html` line 312 also adds `aria-label="Dismiss"`, `key-cover-overflow-menu.html` line 237 has `title` + `aria-expanded`). Good.

- **medium** — The accordion chevron (`ChevronDown`, DESIGN.md line 198) is purely decorative per the header-is-the-button model (see §3), but neither spine explicitly states `aria-hidden="true"` on the chevron SVG to prevent screen readers from announcing a meaningless icon name/glyph inside the header button's accessible name. _Fix:_ Add to EXPERIENCE.md's accordion row: "the `ChevronDown` icon is `aria-hidden="true"`; the header `<button>`'s accessible name comes from the type name + count text only (e.g., 'Lodging, 2 reservations, expanded')."

- **medium** — The confirmation-code chip's `Wallet`-style icon (DESIGN.md line 213, mock `.res-confirmation svg`) is purely decorative but not marked `aria-hidden` in either spine. Same fix as above — low severity individually but part of a pattern; call it out once for "all decorative icons in Reservation rows."

### 5. Keyboard & focus

- **low** — Global `:focus-visible` ring (`outline: 2px solid var(--accent-brand)`, confirmed in `globals.css` line 482-485) is inherited correctly per EXPERIENCE.md line 99, and accordion headers are specified as `<button>`s with `aria-expanded` (line 100). This is solid.

- **high** — Click-to-edit fields (Reservation row provider/anchors/confirmation/notes, DESIGN.md line 217, EXPERIENCE.md lines 57, 84) are specified only as a *mouse* interaction: "click text → inline input... blur/Enter saves, Escape cancels." Neither spine states **how a keyboard-only user enters edit mode** on these fields. A `<span>` or styled `<div>` with a click handler is not keyboard-focusable or activatable by default — this is a known WCAG 2.1.1 (Keyboard) failure pattern. _Fix:_ Add to EXPERIENCE.md's "Reservation row" and "Interaction Primitives" sections: each click-to-edit field is a `<button>` (or has `role="button" tabindex="0"` + Enter/Space handlers) with a visible `:focus-visible` ring, so keyboard users can Tab to it and press Enter/Space to enter edit mode, matching whatever `doc-row.tsx`'s existing inline-rename already does (verify and cite).

- **high** — After Escape-cancel or blur-save on a click-to-edit field, neither spine states where focus goes. The classic click-to-edit failure mode is focus loss (focus lands on `<body>` after the input unmounts) — a serious issue for screen-reader and keyboard users who lose their place in a long Reservation row list. _Fix:_ Add an explicit rule: "On save or cancel, focus returns to the field's display element (the now-restored `<button>`/text), which receives `:focus-visible` — focus never moves to `<body>` or is lost." This is the single most important keyboard fix in this review given how many fields use this pattern (provider, 2 anchors, confirmation, notes — up to 5 per row).

- **medium** — The FR-9 banner's "Add Reservation" button performs a compound action (navigate tab + open a dropdown) on a single activation (EXPERIENCE.md line 61, line 87). Neither spine specifies where keyboard focus lands after this compound navigation — does focus move to the newly-opened type-picker `DropdownMenu`'s first item (so Tab/arrow keys work immediately), or does it stay on a now-unmounted button? _Fix:_ Specify "on activation, focus moves to the first item of the auto-opened type-picker `DropdownMenu`, consistent with standard `DropdownMenu` open behavior when triggered via keyboard."

### 6. Screen-reader semantics

- **high** — EXPERIENCE.md's Accessibility Floor (line 101) gives a good example accessible name for Linked Event rows ("Hotel Check-in — Riverside Inn, Linked, tap to edit in Reservations") but doesn't specify the **mechanism** — is this row a `<button>`/`<a>` with that full string as `aria-label`, or does it rely on DOM order of visually-separate elements (icon, name, badge, meta line) being read in a sensible sequence by default? Given the row contains an icon (potentially not `aria-hidden`), a name span, a badge span, and a meta `<div>`, default screen-reader traversal could read "icon-name [graphic, unlabeled] Hotel Check-in — Riverside Inn Linked Check-in: Tue, Jun 16 · 3:00 PM — from Lodging reservation" — verbose but not incoherent, so this is "high" mainly because the *mechanism* is unspecified, not because the default is necessarily bad. _Fix:_ State explicitly: "the entire Linked Event row is a single `<button>`/link with `aria-label` constructed as `'{anchor label} {time} — {event name}, Linked, opens Reservations'`; the visual icon, name span, badge, and meta line are all `aria-hidden` and the row's accessible name is the single `aria-label`." This avoids double-announcement of "Linked" (once from the badge text, once if also in aria-label).

- **medium** — Accordion expand/collapse: EXPERIENCE.md states headers are `<button>`s with `aria-expanded` (line 100) — correct mechanism — but doesn't specify the accessible name includes the **count** ("Lodging, 2 reservations") so a screen-reader user knows how many rows to expect before expanding. The count badge (DESIGN.md line 198, "22px height... 11px weight 600") is purely visual; without it folded into the button's name, a screen-reader user hears "Lodging, collapsed" with no count. _Fix:_ Accessible name = "{Type name}, {count} reservation(s), {expanded|collapsed}" — count badge `aria-hidden`, value folded into the button label.

- **medium** — Confirmation-code chip (DESIGN.md line 213): the `Wallet`-style icon plus mono-formatted code "AVP-22971-LIS" — mono fonts with letter-spacing can cause some screen readers/voices to spell out or mis-segment alphanumeric codes character-by-character in unexpected ways depending on punctuation handling of the hyphens. Not unique to this feature, but worth a note since this is a *new* UI pattern. _Fix:_ No spec change required, but consider whether the confirmation code should have an `aria-label` like "Confirmation code AVP dash 2 2 9 7 1 dash LIS" only if testing reveals odd pronunciation — flag as a test-time check, not a blocking spec issue (low/informational).

- **medium** — Date/time anchor format "Check-in: Tue, Jun 16 · 3:00 PM" (DESIGN.md line 212, decision log line 21) — the `·` (middle dot) separator between date and time is a Unicode character that some screen readers announce as "middle dot" or skip silently depending on voice/verbosity settings; this is existing precedent from `day-card.tsx` so likely already accepted, but for the *new* Linked Event meta line specifically ("Check-in: Tue, Jun 16 · 3:00 PM — from Lodging reservation", DESIGN.md line 246) there's now also an em-dash before "from Lodging reservation" — two non-alphanumeric separators in one string read aloud. _Fix:_ If this hasn't already been validated for `day-card.tsx`'s existing anchor format, do so now since the Linked Event meta line is longer and adds a second separator; otherwise no new risk beyond existing precedent.

- **high** — FR-9 banner's combined "navigate to Reservations tab + auto-open the type-picker dropdown" (EXPERIENCE.md lines 61, 87, decision log line 22, line 26) is an abrupt, double context-change triggered by a single tap, with **no screen-reader announcement specified**. A screen-reader user activating the button would have the page/route change underneath them and a dropdown open, with no `aria-live` announcement of "Navigated to Reservations. Reservation Type menu opened." — they could be confused about what just happened (focus inside a dropdown on an unfamiliar tab). _Fix:_ Add to EXPERIENCE.md's FR-9 row: "On activation, an `aria-live=\"polite\"` region (or the route-change announcement Packt already uses for tab navigation, if one exists) announces the tab change before the dropdown opens; focus then moves into the dropdown's first item per the §5 fix above."

### 7. Forms

- **medium** — Required vs. optional field distinction (DESIGN.md line 143, "Field label... with a teal `*` for required fields and a muted 'Optional' suffix... for optional fields") is purely visual/textual-suffix. The teal `*` alone is a classic accessibility gap (color + glyph, not programmatically tied to the input), though the "Optional" text suffix is good practice. Neither spine states that the corresponding `<input>`/`<textarea>` elements carry `aria-required="true"` (for required fields) or that the `*`/"Optional" text is included in the field's accessible label (e.g., via `aria-describedby` or being part of the `<label>` text itself, not a sibling span that might not be associated). _Fix:_ Add to DESIGN.md or EXPERIENCE.md's drawer section: "Required fields' `<input>`/`<textarea>` carry `aria-required=\"true\"`; the `*`/'Optional' suffix text is part of the `<label for=...>` element (or referenced via `aria-describedby`) so it's announced as part of the field's name, not lost as a disconnected visual glyph." This is consistent with `trip-edit-sheet.tsx`'s existing `form-section.tsx` pattern if that already does this — cite it.

- **high** — Time-anchor `input-row` pairs (DESIGN.md line 229: "two `h-9` inputs side by side (date with `Calendar` icon, time with `Clock` icon)") — each pair shares one `<label>` ("Check-in*") but renders as two separate `<input>` elements. Neither spine states how each individual input is labeled for assistive tech — a screen reader encountering the second (time) input in isolation needs to know it's "Check-in time" not just "time," especially since Tab order will land on it without re-announcing "Check-in." _Fix:_ Specify: "Each anchor's date input has `aria-label=\"{Anchor label} date\"` (e.g., 'Check-in date') and the time input has `aria-label=\"{Anchor label} time\"` ('Check-in time'); the visible `<label>` text ('Check-in*') applies to the field group via `aria-labelledby` or a `<fieldset>`/`<legend>` wrapping both inputs." This is a new pattern for Packt (first paired date+time inputs) so it needs an explicit rule rather than relying on precedent.

- **low** — The Documents empty state inside the drawer (DESIGN.md line 232, mock `.doc-empty`) reuses `trip-docs-tab.tsx`'s composition — EXPERIENCE.md correctly notes "matches Documents-tab tone" for copy (line 46). No new accessibility concern beyond what's already shipped for that pattern, assuming it's already accessible.

### 8. Motion/dismissal

- **medium** — FR-9 banner's "navigate + auto-open dropdown on single tap" (decision log lines 22, 26; EXPERIENCE.md line 61, 87) is a **change of context initiated by user request** (WCAG 3.2.2 "On Input" is about *unrequested* changes — a deliberate button tap is "on request," so this technically doesn't violate 3.2.2 in the strict sense). However, the *combination* of two changes (tab navigation + dropdown auto-open) from one tap could still surprise users who expect "Add Reservation" to mean "go to the Reservations tab" and are then unexpectedly also presented with an open menu requiring a second decision. _Fix:_ This is more a UX clarity note than a hard WCAG violation — no blocking fix required, but consider (non-blocking) whether the dropdown auto-open should be preceded by a brief visual settle (tab transition completes, *then* dropdown opens) rather than simultaneous, so the context change reads as sequential rather than instantaneous/disorienting. Document the sequencing explicitly either way so implementers don't have ambiguity.

- **low** — Dismiss behavior for the FR-9 banner: decision log line 22 flags "dismissible" persistence (session vs. cross-session) as an open `[ASSUMPTION]`. From a pure accessibility lens (rather than product), once dismissed, screen-reader/keyboard users need a way to re-surface the banner if they dismissed it accidentally (e.g., via a fat-finger tap near the `X`) — there's no stated "undo" or way to re-show it within the session. _Fix:_ Not blocking, but if the assumption is resolved as "session-only dismiss," confirm there's some recovery path (e.g., banner reappears on next tab visit, or a setting). If "permanent dismiss," an accidental dismiss has no recovery — slightly riskier for users with motor-control difficulty who may mis-tap the `size-8` dismiss button (which sits only 8px from other content, mock line 166-167 `top: 8px; right: 8px`).

## What's already handled well

- The Linked Event indicator redesign (icon-swap + neutral "Linked" badge, no color-only signal, no left-border/tint) directly resolves a real color-as-sole-signal risk and is explicitly documented as redundant in EXPERIENCE.md's Accessibility Floor — don't revert to the rejected violet-token treatment.
- `title` attributes on all three icon-only controls (doc-upload, FR-9 dismiss, Cover Overflow trigger) are present in both spines and mocks, including `aria-label` on the FR-9 dismiss button in the mock.
- Tap-target floors are explicitly enforced and corrected where the mock under-sized them (28px doc-upload → 32px per EXPERIENCE.md line 98) — this self-correction shows the floor is being actively checked, not just assumed.
- Accordion headers as `<button>` with `aria-expanded`, global `:focus-visible` ring inheritance, and keyboard-navigable Base UI `DropdownMenu`/`Drawer` primitives are all correctly called out as the baseline — no custom focus/keyboard reinvention proposed.
- "Happening now" remains the single accent-colored state, explicitly protected in the Do's/Don'ts table — prevents accent-color dilution that would otherwise reduce the "now" signal's salience.
