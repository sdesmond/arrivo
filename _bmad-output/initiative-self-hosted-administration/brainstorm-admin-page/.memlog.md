- (idea by user) Add an admin page for managing users and common self-hosted application needs.
- (direction by user) Creative Partner mode; coach chooses techniques. Session belongs to Self-hosted administration initiative.
- (technique by coach) Started Job to Be Done: explore underlying admin jobs. Planned next: Mind Mapping to expand capability areas; Failure Analysis to uncover operational and recovery needs.
- (idea by user) First admin job: add other users to the application.
- (idea by coach) Admin could issue an invite link so a new user sets their own password without requiring email delivery.
- (idea by user) Admin supplies email and possibly username, then forwards an invitation link to the new user.
- (decision by user) Admin can rescind a pending invitation. No email integration for now, so no in-app resend action; admin forwards links manually.
- (idea by user) Admin should be able to delete users and possibly view logs. Logging does not currently exist and should be added.
- (idea by coach) Audit log could record who invited, rescinded, or deleted a user and when, providing an initial useful logging scope.
- (direction by user) App-wide logging is a larger future effort; start with an admin-visible audit log of user activity: login/logout, trip creation/modification, invitation creation/acceptance, password changes, and username changes.
- (idea by coach) Audit entries could show actor, action, affected user or trip, time, and outcome, without recording passwords or full trip contents.
- (decision by user) Admin-initiated account deletion should reuse the recently implemented self-service account deletion flow, including handling owned and shared trips. Consult existing behavior during design rather than inventing a separate policy.
- (insight by coach) Comparable self-hosted apps: Immich supports admin password resets, storage quotas, user management, jobs monitoring, and recovery commands (https://docs.immich.app/administration/user-management/ ; https://docs.immich.app/administration/jobs-workers/ ; https://docs.immich.app/administration/server-commands/). Paperless-ngx exposes users/groups, admin logs, system status, and separate aggregate statistics permissions (https://docs.paperless-ngx.com/usage/).
- (technique by coach) Started Mind Mapping: expand beyond invitations, user deletion, and activity logs using comparable self-hosted application patterns.
- (idea by coach) Potential Arrivo admin branches: manually shared password-reset links; reversible account suspension and session revocation; admin promotion/demotion with last-admin protection; instance health/version/storage overview; registration and upload-limit controls. Suggestions remain unselected.
- (decision by user) Include account recovery, managing admins, and instance overview among administration capabilities to explore. Suspension and instance controls were not selected.
- (decision by user) On a fresh installation, the first account created becomes admin.
- (direction by user) Arrivo is pre-alpha. Only relevant existing installation has one account. No multi-account legacy admin-selection flow is needed; existing sole account can become admin.
- (decision by user) Public signup closes after first account is created. All subsequent accounts require admin creation through the invitation flow.
- (idea by coach) Instance overview suggestions: database connectivity and document-storage read/write health; user/admin/pending-invite counts; trip/document counts and stored document bytes; recent failed logins and admin actions; last successful backup only if Arrivo can reliably observe it. Lead with health, account counts, and storage usage; expand into detail on demand.
- (decision by user) Accepted proposed initial instance overview: database and document-storage health, user/admin/pending-invitation counts, trip/document counts and storage usage, recent admin actions and failed logins. No additional overview ideas offered; backup status remains a possible later addition.
- (technique by coach) Started Failure Analysis: examine admin lockout and account recovery failures to find missing operational needs.
- (idea by coach) Provide a server-side recovery command for the sole admin who forgets their password, since no other admin or email delivery may be available.
- (direction by user) User is unsure how sole-admin account recovery should work; needs a recommendation.
- (idea by coach) Recommend server-side command that generates a short-lived, single-use password-reset link for an existing admin. Operator runs it through host or Docker access, opens link, and chooses new password; successful reset revokes existing sessions. Pair with preventing deletion or demotion of last admin.
- (idea by coach) Alternative sole-admin recovery designs: interactive server command sets a new password directly (no browser link, requires terminal access); one-time recovery codes generated at setup and stored offline (no server access needed but codes can be lost or stolen); temporary server-enabled recovery mode authorizes a local reset (more configuration and cleanup). A second admin offers routine recovery but is not sufficient as sole emergency mechanism. Prefer interactive password-reset command for initial scope.
- (insight by coach) CLI recovery trust boundary is server/container administration access or application database credentials, not Arrivo login. Ordinary web users cannot invoke a CLI-only command; someone controlling deployment or database can already alter accounts. Restrict host/Docker and DB access; expose no web reset bypass. Docker security guidance: https://docs.docker.com/engine/security/ . Recovery should record audit event and revoke sessions.
- (decision by user) Accepted server operator as trusted authority for emergency account recovery. Use server-side CLI recovery gated by deployment/database access; no unauthenticated web recovery bypass.
- (decision by user) Admin status preserves existing trip sharing permissions; it does not grant access to every user trip or its contents.
- (idea by coach) For trips an admin cannot otherwise access, audit log can show actor, action, timestamp, and opaque trip identifier while omitting trip title, destinations, and edited values.
- (decision by user) Provisionally accepted audit metadata for trips outside admin sharing access: actor, action, timestamp, and trip ID; omit titles, destinations, and changed values.
- (technique by coach) Started MoSCoW convergence to propose first-release scope and later work.
- (direction by coach) Proposed first-release scope: first-admin bootstrap and invite-only registration; invite creation/copy/rescind; user list and deletion using existing flow; admin promotion/demotion with last-admin protection; manually shared password-reset links and emergency CLI reset; selected activity events with private-trip metadata limits; version, health, counts, storage, and recent activity overview. Defer email delivery, broad diagnostic logging, suspension, quotas, backup integration, offline recovery codes, and recovery mode. Await user scope verdict.
- (decision by user) Approved proposed first-release scope: onboarding and invite-only registration; user list/deletion reusing existing flow; admin management and last-admin protection; password-reset links and emergency CLI reset; scoped activity log preserving trip privacy; instance overview. Deferred email integration, broader diagnostic logging, suspension, quotas, and backup integration.
- (insight by user) Central idea tying this initiative together is user management.
- (insight by coach) User management provides organizing spine: invitations control entry, admin roles govern authority, deletion governs exit, recovery restores access, activity logs explain account actions, and instance overview supports operation. Existing trip permissions remain independent from admin status.
