- (decision) JTBD: let trip owners share a private, always-current itinerary with specific people without shared credentials or in-person coordination
- (capability) CAP-1: manager shares a trip with a person by email; existing users get in-app invite, unmatched emails get email invite with signup route; new invitation defaults to viewer role
- (capability) CAP-2: invited person accepts an email-bound invitation link and lands on the shared trip overview showing trip identity, sharer, and their access level; a different account cannot accept the link
- (capability) CAP-3: viewer opens and reads a shared trip's itinerary (days/events/locations) with no money, budget, or budget-report data, and cannot mutate itinerary, delete trip, or manage contributors, enforced server-side
- (capability) CAP-4: editor views and mutates itinerary and budget/money items on a shared trip but cannot delete the trip or manage sharing/membership, enforced server-side
- (capability) CAP-5: manager holds owner-equivalent full access: edit trip, delete trip, invite/remove contributors, change contributor roles, enforced server-side
- (capability) CAP-6: manager administers all contributors and pending invitations from one share dialog listing role/status, supporting role change, removal, and resend; changes stage and require explicit Save or Cancel, cannot dismiss with unsaved changes
- (capability) CAP-7: pending invitations expire after a global 72-hour setting; a pending invite removed before acceptance shows the recipient a rescinded message instead of granting access
- (capability) CAP-8: shared trip state (itinerary/events/locations, membership, roles) updates live across sessions without reload; when live sync cannot operate, an offline/internet-down indicator shows in the status bar
- (capability) CAP-9: removing a contributor immediately revokes access -- trip disappears from their dashboard/shared list; if actively viewing, a modal names the trip owner, directs them to request resharing, OK returns them to their dashboard, and browser Back cannot reopen the trip
- (capability) CAP-10: concurrent edits to the same itinerary item from multiple contributors resolve latest-write-wins, converging all sessions to that state
- (constraint) trips are private by default; access is manager-issued only, no public discovery or access-request flow
- (constraint) role boundaries (viewer/editor/manager) are enforced server-side, not only in the UI
- (constraint) invitation entry is email-only this release; no friend/user picker
- (constraint) invitation links bind to the invited email address; an account with a different email cannot accept it
- (constraint) invitation expiry (72h) is one global application setting, not manager- or per-invite-configurable
- (constraint) contributor access persists after trip completion until a manager explicitly removes it -- no automatic expiry
- (constraint) share dialog cannot dismiss while staged role/removal changes are unsaved -- must Save or Cancel
- (constraint) concurrent edit conflicts resolve latest-write-wins, no merge UI
- (non-goal) public trip discovery or contributor access-request flow
- (non-goal) forwardable invitations usable by an account other than the invited email
- (non-goal) per-invitation or manager-chosen expiration times
- (non-goal) automatic contributor-access removal after trip completion
- (non-goal) message center/notification surface for sharing events (deferred future idea, not part of this spec)
- (non-goal) friend/known-user picker as alternative to email entry (deferred future idea)
- (non-goal) viewer PDF export of itinerary (deferred, contingent on an export capability that does not yet exist)
- (non-goal) making invitation expiry itself configurable beyond the fixed 72-hour global default (open product decision, deferred)
- (decision) success signal: all contributors on a shared trip track trip progress -- current events, locations, itinerary -- live and in sync; role boundaries hold at server/API layer including mid-session revocation and live-sync failure
- (question) phasing note from source task list: viewer-sharing + live sync is the Must/first-release slice; editor/manager roles and full share-dialog administration are Should/follow-on within the same contributor model -- both are captured as capabilities here, sequencing is a Story Breakdown decision, not a spec scope cut
