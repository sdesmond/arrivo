# Trip-edit Activity batching serializes per actor/trip key with a transaction advisory lock

Routine trip edits collapse into one "Updated trip" row per actor and trip with a ten-minute inactivity window, and concurrent edits can arrive in any order. Row locks cannot cover the case where no row exists yet, so each merge takes a transaction-scoped advisory lock keyed on the actor/trip pair and computes an interval union over the rows it touches. Arrival order then cannot change the result, and no two same-key rows stay within the gap, so one new event bridges only the rows it touches. The cost is that same-key writers queue, so a queued writer sets its own `lock_timeout` (4 s, below the 5 s caller timeout) because the caller's timeout only abandons the promise and would otherwise leave the connection pinned behind a stuck holder.
