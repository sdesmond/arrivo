# Documents have one scope

Date: 2026-11-14. Status: accepted (decided 2026-11-12).

A document belongs to exactly one scope: the trip, one event or one reservation. The earlier web actions could leave both an event link and a reservation link set, and the code resolved such a row's trip inconsistently: `documentTripId` fell back event-first while the mapper gave the reservation precedence. In the v1 contract, `PATCH /api/v1/documents/:documentId` takes `eventId` or `reservationId` as an absolute value and setting one clears the other; sending both, including both as `null`, is 422; either one set to `null` promotes the document to trip scope; a target in another trip is 404; `linked-*` event ids are refused. A legacy row that already has both links is normalized on its first effective change, with no backfill. The plans and `deferred-work.md` give the reason as removing that dual-link state and the wrong-scope authorization it allowed; they do not record alternatives considered, so no reason beyond that is claimed here. This is hard to reverse because API clients will depend on it.
