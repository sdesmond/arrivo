# Trip date changes confirm through a 409 and an echoed confirmation

Date: 2026-11-21. Status: accepted (decided in story 5.7, PR #556).

Shrinking or moving a trip's dates can remove days that hold events, notes, checklists or overlapping reservations, and an API client has no dialog the server can open. `PATCH /api/v1/trips/:tripId` therefore answers a date change that would remove content with 409 `confirmation_required`, writing nothing, and carries a `confirmation` object in the error body: the removed dates or day labels, the events and reservations affected, and counts of notes, checklists and files. The client applies the change by sending the same request again with a `resolution` (`delete-events` or `keep-as-unscheduled`) and that `confirmation` echoed back unchanged. The service throws `ConfirmationRequiredError` from inside the locked write, so the transaction rolls back and no idempotency replay record is stored, and it recomputes the confirmation under the trip lock on the applying request: if the recomputed value differs from the echo (compared with `stableStringify`), the trip changed since the preview and the response is 409 `conflict`. This keeps the decision on one endpoint with no separate preview route or server-side preview token to store and expire, and the echo proves the client showed the user what is about to be removed. The trade-off is that a client must send each confirming request twice and keep the payload opaque, and that any field added to the confirmation changes what a stale echo looks like, so clients must echo the object they received rather than rebuild it.
