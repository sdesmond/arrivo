# Packing order is a full-list PUT with each item's section

Date: 2026-11-21. Status: accepted (decided in story 5.2, PR #549).

The packing drag-reorder server action accepted partial or stale lists, so one editor's drag could silently overwrite another editor's add, delete or move. `PUT /api/v1/trips/:tripId/packing/order` now takes one list's complete order as `[{ id, labelId }]`, where the array index is the position and `labelId` is the item's section (`null` for ungrouped and for section labels themselves), up to 1000 rows. The server compares the id set with the rows the list holds right now: a missing, extra or foreign id returns 409 `conflict` and writes nothing (a duplicate id is 422 `validation_failed`), so the client reloads instead of overwriting; a list already in that order and grouping writes nothing and records no activity. Sending the section with each row lets one request express a drag across sections, which a position-only order cannot. The comparison is on the id set only, so the same ids in a new order succeed and the last write wins between two pure reorders; the review rejected comparing order too, since the matrix defines stale as a set mismatch. A full list costs a body proportional to the list and up to 1000 position updates, accepted because packing lists are small and every queued drag stays safe on its own, so the client needs no cancel logic for drags queued after a failure. Source: plan `story-reorder-packing-items-through-the-api-plan.md` (story 5.2, Intent and Review Triage Log), commit `886f2c3d`, merge `0653803e`, and `src/lib/services/packing.ts`.
