# File deletions survive the transaction commit

Date: 2026-11-14. Status: accepted (decided 2026-11-12, in story 2.5).

A database row and its stored file cannot be removed in one transaction. An event delete used to remove its documents' files after the commit, so a crash in between lost the file names for good. The file URLs are now queued in the deleting transaction in the `pending_file_deletions` table (`queueFileDeletions`), the files are removed only after the commit (`removeQueuedFiles`), a queue row is cleared once its file is gone, and the maintenance pass retries what is left (`drainPendingFileDeletions`), moving a row that fails to the back of the queue so one permanently failing file cannot starve newer ones. A rollback queues nothing, so no file is removed for a change that did not happen. Document removal, event delete, reservation delete, and cover select, remove and replace all use it. The trade-off is a table and migration `0014`, which story 2.5 recorded as an exception to its no-migration boundary; the reason in commit `3b2f9f4d` is that a process dying between the commit and an in-memory cleanup lost the file names for good, and the plans record no alternative beyond that earlier closure. Source: plan `story-create-and-delete-events-through-the-api-plan.md` (story 2.5, Plan Change Log of 2026-11-12), commit `3b2f9f4d`, commit `151b60c4` for the retry order (story 3.8), and `src/lib/file-cleanup.ts`.
